## Context

См. `proposal.md` — Why. Здесь только то, что определяет форму решения.

**Чат сегодня.** `chats` — плоский список (`id`, `title`, `model`,
`effort`), `chat_msgs` с ролями `user`, `assistant`, `peer` (реплика
собеседника), `sent` (что ушло собеседнику), `note`, `tool`. Чат
мессенджера заводится `tgChatFor`/`maxChatFor` и привязан к
`tg_chats`/`max_chats`, где живут права `Collect/Reply/Send/Files/
Blocked/Admin`. Написанное человеком уходит собеседнику сразу
(`tgSendByHuman`), слово вызова (`tg.help_word`) уводит реплику Сёме,
ответ и карточки ложатся в тот же чат. Автоответ — `tgAutoReply`, ответ
уходит собеседнику и ложится как `sent`, человек получает уведомление.

**Что знают слои мессенджеров.** `tg.Update` — чат, вид (`user|group|
channel`), номер, текст, `Out`, файл; ни `reply_to`, ни топика. MAX —
диалог, чат, канал; ни ответов, ни комментариев. gotd умеет
`channels.getForumTopics`, `messages.getDiscussionMessage`, `reply_to` с
`top_msg_id` — сантехника есть, но не подключена.

**Экраны.** `buildChat` — пузыри по ролям, поле с подсказкой «кому
уйдёт», меню чата. Список чатов группируется: Telegram, MAX, Разбор
уведомлений, Задачи, Мои чаты; у `Пункт` есть `Вложен`. Словарь UI-DSL
зафиксирован версией: новый тип компонента — пересборка приложения.

**Память.** У каждого чата своя сессия; чат удаляется только после
сводки. `AddChatMsg`/`continueChat`/`saveToolCard` зовутся из 57 мест.

## Goals / Non-Goals

**Goals:**

- Переписка с людьми и разговор с Сёмой про неё лежат порознь; слово
  вызова никогда не уходит собеседнику.
- Топики групп и посты каналов с комментариями — отдельные разговоры с
  правильным адресом ответа.
- Ветка с Сёмой по конкретному сообщению — в любом чате.
- Ничего из сегодняшней истории не теряется и не переезжает.
- Приложение не пересобирается.

**Non-Goals:**

- Тред «Сёма» как настоящий топик в самом Telegram: у личных чатов топиков
  нет, а в группах это выдало бы разбор всем участникам.
- Треды глубже одного уровня под разговором.
- Ведение канала (публикация постов от имени человека) — это «писать
  первым» в канал, отдельное право и отдельный разговор, не здесь.

## Decisions

### 1. Три уровня в одной таблице: контейнер → разговор → тред

`chats` получает `parent_id`, `kind` и два якоря: `anchor_msg_id` (наше
сообщение-якорь у треда по сообщению) и `topic_id` (номер топика или
поста в мессенджере). Виды:

| kind | что это | лента | родитель |
|---|---|---|---|
| `""` | обычный чат Сёмы | своя | нет |
| `dm` | личный чат мессенджера | переписка | нет |
| `group` | группа с топиками | **нет** | нет |
| `channel` | канал | **нет** | нет |
| `topic` | топик группы | переписка | `group` |
| `post` | пост канала с комментариями | пост + комментарии | `channel` |
| `sema` | тред «Сёма» | разговор с Сёмой | разговор |
| `msg` | тред по сообщению | разговор с Сёмой | любой чат с лентой |

Группа без топиков — один разговор `dm`-вида с `kind = group` и лентой:
контейнер появляется только когда у группы включены топики. Правило
«одна глубина» переформулировано: тред всегда на один уровень ниже
**разговора**, контейнер лентой не владеет.

Альтернатива — отдельные таблицы под топики и посты — удвоила бы каждый
путь: контекст, карточки, память, экраны. Отвергнута.

### 2. Что куда ложится

Одно правило: **в ленте разговора только то, что собеседники видели или
увидят.** Всё, чего они не видят, — в треде «Сёма» этого разговора.

| Событие | Лента разговора | Тред «Сёма» |
|---|---|---|
| реплика собеседника / пост / комментарий | `peer` | — |
| вы написали собеседнику | `sent` | — |
| «Сёма, …» из поля ленты | — | `user` |
| ответ Сёмы | — | `assistant` |
| карточки команд, таймеры, скиллы, память | — | `tool` |
| черновик ответа собеседнику | — | карточка «Отправить» |
| черновик подтверждён и ушёл | `sent` | карточка «отправлено» |
| автоответ с правом «Отвечать» | `sent` | разбор + карточка «отправлено» |
| админ-чат: команда хозяина | `peer` | `user` → `assistant`; ответ хозяину — `sent` |
| заметка (`note`) | — | `note` |

Точка входа одна: `chatForOutput(chatID)` — для разговора из мессенджера
возвращает его тред «Сёма» (заводит при первом обращении), для
остальных — сам чат. Через неё идут все 57 мест записи; править их по
одному — значит пропустить три.

### 3. Слово вызова ведёт в тред, экран идёт за ним

Поле ленты по-прежнему пишет собеседнику, подсказка «кому уйдёт»
остаётся. Строка со словом вызова уходит в тред «Сёма» вопросом, ответ
действия открывает тред: человек видит, куда ушло. В треде поле пишет
Сёме без слова, подпись — «Написать Сёме · собеседник этого не видит».
Отправить собеседнику из треда можно только черновиком с кнопкой.

### 4. Топики Telegram — разговоры под группой

У входящего появляется `TopMsgID` из `reply_to` (при `forum_topic`) —
это и есть номер топика; список и названия — `channels.getForumTopics`,
обновляется вместе со списком чатов. Разговор `topic` заводится при
первом сообщении в топике (лениво, как чаты сейчас), «Общий» топик — тоже
разговор. Отправка в топик — с `top_msg_id`; `tgSendByHuman` и черновики
берут его из разговора. Якорь контекста топика — его первое сообщение
(название топика в подписи).

### 5. Посты каналов — разговоры под каналом

Пост канала — разговор `post` с якорем-постом; комментарии приходят из
привязанной группы обсуждения с `reply_to.top_msg_id` = сообщение поста
в этой группе, а `messages.getDiscussionMessage` сшивает его с постом
канала. Пост без комментариев — разговор из одного сообщения; посты
старше `tg.post_days` (30) не заводятся разговорами, а читаются как
история канала. MAX: пост канала — тот же разговор `post`; есть ли в его
API комментарии, проверяется первой задачей этапа 3 — если нет, MAX
остаётся на постах без веток, и это записано.

**Сделано 11 сентября 2026 (Telegram, задачи 4.2, 4.3, 4.5).** Что
уточнилось на коде:

- Привязка живёт в своей таблице `tg_post_links` (канал + пост → группа
  обсуждения, её `access_hash` и номер копии поста), с индексом по паре
  «группа + корень»: входящий комментарий узнаёт свой пост одним
  запросом к базе. `getDiscussionMessage` зовётся один раз на пост,
  отдельным заходом (`tgLinkPost`) — входящее сообщение ждать сети не
  должно; после привязки оттуда же подтягиваются уже написанные
  комментарии.
- **Разговор и права у канала, физический адрес — у группы обсуждения**
  (`tgAddr`). Разделение неизбежное: комментарии живут в другом чате, и
  класть их в архив под номером канала нельзя — номера сообщений двух
  чатов в паре «чат + номер» столкнулись бы, и комментарий молча затёр
  бы пост. Поэтому архив физический (чат, откуда пришло, и номер в нём;
  тема комментария — корень ветки), а отправка идёт в группу ответом на
  копию поста.
- **Копия поста, которую Telegram сам кладёт в группу обсуждения,
  пропускается** (`tgRoute` → `skip`): пост уже первым сообщением своего
  разговора, второй раз его показывать незачем.
- **Своих прав у поста нет** — он живёт правами канала. Отступление от
  решения 6 сделано нарочно: канал даёт сотни постов, и тумблер на
  каждый был бы списком, который никто не читает. У топиков
  переопределения остались.
- **В сам канал Сёма не пишет** (`tgCanReply`): это ведение канала —
  отдельное право, вынесенное в Non-Goals. Ответ под постом, у которого
  группа обсуждения не найдена, тоже отказ, и он назван словами, а не
  ошибкой Telegram.
- **Прежняя плоская лента канала** (канал мог собираться до этого
  изменения) уезжает в разговор «Лента канала» под контейнером — ровно
  как переписка группы уезжает в «Общий». У контейнера ленты нет, и
  иначе собранное пропало бы с экрана.
- **Канал не ждёт ответа**: он вынут из семафора «Ждут ответа»
  (`tgWatchedPeers`). Посты идут потоком, ответа на них не бывает, и
  семафор горел бы на канале всегда.

### 5а. API MAX: комментарии есть, но не в той двери (задача 4.1)

Разведка 11 сентября 2026 по официальным источникам.

**Чем Сёма говорит с MAX сегодня.** `internal/max/max.go` — это не Bot
API, а клиентский протокол веб-клиента: WebSocket на
`wss://ws-api.oneme.ru/websocket` с `Origin: https://web.max.ru`, бинарный
JSON с опкодами (`opInit`, `opCodeAsk`, `opLogin`, `opHistory`, `opChats`,
`opSend`, `opFileUp`). Постов, комментариев и обсуждений в нём Сёма не
знает вовсе — из структуры чата известен только вид `channel`.

**Что есть в публичном API MAX.** В **Bot API** (`dev.max.ru/docs-api`)
комментарии к постам каналов — отдельный, прямо названный набор:
`GET|POST|PUT|DELETE /messages/{messageId}/comments`,
`GET /messages/{messageId}/comments/{commentId}`, события подписки
`comment_created`, `comment_edited`, `comment_removed`. Подтверждено не
пересказом страницы, а исходниками официальной Go-библиотеки
`max-messenger/max-bot-api-client-go`: `const.go`
(`formatPathComments = "/messages/%s/comments"`), `comments.go`
(`GetComments`, `GetCommentByID`, `Send`, `Edit`, `Delete`),
`model/comment.go` (`CommentRecipient{ChatID, ChatType, PostID}` — комментарий
привязан к посту), `model/types.go` (`ChatTypeChannel = "channel"`,
константы событий). На уровне продукта комментарии в каналах MAX тоже
есть и устроены похоже на Telegram — отдельным чатом обсуждения, куда
пост пересылает бот (это вторичные источники, не офдока).

**Открытого клиентского (user) API у MAX нет** — в общедоступной
документации задокументирован только Bot API; протокол, которым ходит
Сёма, отреверсен с веб-клиента.

**Вывод и что из него следует.** Комментарии в MAX есть, но не за той
дверью, в которую Сёма стучится. Читать их нынешним клиентским
протоколом нечем: чтобы получить `comment_created` и отправить
комментарий, нужен **бот, добавленный в канал**, и Bot API рядом с
нынешним соединением — своя авторизация, свой токен, свои права. Это не
«дописать диалект переходника», а второй канал связи с MAX.

Поэтому задача 4.4 **не начата**: диалект, написанный по документации
без живой проверки, был бы выдумкой, а выдуманный диалект хуже
отсутствующего. Когда за MAX возьмутся, начинать надо не с постов, а с
решения «заводим ли бота»: без него посты MAX остаются разговорами без
веток, как и записано в решении 5.

### 6. Права — контейнеру, переопределение — разговору

`Collect/Reply/Send/Files/Blocked` остаются у `tg_chats`/`max_chats`
(контейнер или личный чат). У разговора — переопределения тех же полей
(`NULL` — как у родителя). Экран настроек мессенджера показывает топики
и посты под контейнером с тумблерами; правило «спрашивают, можно ли
писать самой Сёме» не меняется. Автоответ смотрит на права разговора.

### 7. Тред по сообщению

Действие «Обсудить с Сёмой» в меню пузыря (`thread_from_msg`) находит
тред `msg` с этим якорем или создаёт, кладёт вводную `note` с текстом
якоря и открывает. Один якорь — один тред. Контекст: якорь целиком, хвост
родительского разговора (`chats.thread_tail`, 12), сама ветка; в промпте
подписаны «родитель» и «ветка».

### 8. Экраны без новых типов словаря

- Контейнер: список разговоров строками (`row`) с датой и счётчиком,
  кнопка «Настройки» — в настройки мессенджера.
- Разговор: как чат сегодня плюс строка «Тред «Сёма» · N реплик» и
  действие «Обсудить с Сёмой» у пузырей; у поста первым пузырём — сам пост
  с капсулой «пост».
- Тред: подпись «ветка разговора «…»» с переходом наверх; у треда по
  сообщению якорь первым пузырём с капсулой «по сообщению».
- Список чатов: контейнер → разговоры вложены → треды вложены под
  разговором; три уровня на телефоне проверяются макетом до кода
  (правило проекта «сначала дизайн»).

### 9. Память и удаление

Тред — свой чат со своей сессией; наследует модель, усилие и области
разговора. Удаление разговора закрывает сводкой и удаляет треды;
удаление контейнера — разговоры с тредами. Пинатель и сроки чатов
команд действуют на треды.

### 10. Переезд и этапы

Сегодняшние смешанные ленты остаются как есть: переносить задним числом
— гадать. Новое ложится по правилу 2 с выката. Этапы: (1) `dm` и тред
«Сёма», тред по сообщению — закрывает сегодняшнюю беду; (2) топики
Telegram; (3) каналы Telegram и MAX. Настройки `chats.thread_tail`,
`tg.post_days` — на вкладках «Уведомления» и «Telegram».

## Risks / Trade-offs

**Три уровня на телефоне.** Список чатов станет глубже. → Макет до кода;
контейнеры сворачиваются, треды показываются только у открытого
разговора.

**Комментарии Telegram живут в другой группе.** Привязка через
`getDiscussionMessage` — лишний вызов на каждый первый комментарий к
посту. → Кэш пары «сообщение группы обсуждения → пост» в разговоре.

**MAX может не иметь комментариев.** → Первая задача этапа 3 — проверка
API; без комментариев посты остаются разговорами без веток, честно
названо.

**Два поля ввода — две адресации.** → Подпись поля треда и отправка
собеседнику только черновиком.

**57 мест записи в чат.** → `chatForOutput` одна; тест перебирает
вызовы `AddChatMsg` в `engine` и требует либо `chatForOutput`, либо
пометку `// в тред уже выбран` — по образцу
`TestNoFourthGate`.
