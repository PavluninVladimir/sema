## Context

Зачем это нужно — см. proposal.md («Why»). Здесь только то, что определяет
устройство.

- **Jev — не чат-модель.** Свой API `POST https://api.typesafe.ai/v1/systemone`:
  `{state, model, questions}`, ключ Bearer. Вопросы трёх видов: `choice`
  (до 255 вариантов → вариант, вероятности, `confidence`), `score` (2–10
  упорядоченных уровней → позиция, вероятности, `confidence`), `noul` («да или
  нет» → одно число 0–1). Вопросы одного запроса считаются параллельно, а
  `state` оплачивается один раз. Контекст — 64 тыс. токенов, из них на
  `state` — 32 тыс. Цена: вход $0.042 / 1M, выход бесплатно. Ошибки 401 / 422
  / 429 / 529. Слабости по самой документации (`model-jaggedness/jev-1.13`):
  английский — основной язык, текст читает буквально, даты — как текст, не
  считает, **не считает вход враждебным**, тянется к первому варианту.
  Данные: США, на входах не обучают, режим без хранения — только для
  enterprise.
- **Дверь к модели держится построением.** Любой провайдер достаётся через
  `provider()` и заворачивается в `gate` (`engine/gate.go`), а тот перед
  вызовом спрашивает `BeforeModel`. Обёртка продвигает только объявленные
  методы, поэтому `CompleteImage` у `gate` объявлен всегда — иначе картинки
  молча выключились бы. `TestNoFourthGate` держит, что мимо `provider()`
  провайдера не построить.
- **Спам писем.** `processFetched → matchRule → ragDecide → filterModel →
  classify`. `filterModel` сам отводит закрытые ящики (`mailboxClosedForCloud`)
  и вырезает секретное (`outsideCut`). `Verdict.Confidence` попадает в
  `messages.confidence` и рисует бейдж «спам N %», но ни на что не влияет.
  Повторный разбор писем — `engine/rejudge.go` (`WorkMsgJudge`). Политика
  прежняя: модель помечает, человек подтверждает, похожие уходят сами.
- **Мессенджеры.** Telegram читает только выбранные чаты (`tgWatched`).
  Входящее: `onTGMessage` → архив (`AddTGMessage`) → лента Сёмы → «Ждут
  ответа» (`tg_wait.go`) → автоответ (`tgAutoReply`), где он разрешён.
  Комментарий под постом приходит в группу обсуждения, но принадлежит
  каналу (`tgRoute`, `tgAddr`): права и класс берутся у канала, а класс
  канала — «обычное».
- **Чат.** Модель роли «Чаты» — основная плюс запасная (`Role.Model`,
  `Role.Spare`); запасная зовётся только при отказе основной
  (`AskRoleSpare`). Контекст собирается по худшей из двух моделей
  (`chatCloud`), поэтому недоверенная запасная закрывает закрытое и для
  доверенной основной.

## Goals / Non-Goals

**Goals:**
- Один вид вызова «решение» для всех трёх применений: одна дверь, один
  учёт, один теневой режим и один отчёт.
- Решающая модель ничего не решает необратимо: спам писем по-прежнему
  подтверждает человек, спам в чате только прячется, маршрут может лишь
  удешевить ответ, а не открыть модели больше, чем открыла бы основная.
- Любое применение выключается одной настройкой и возвращается на
  нынешний путь без потери данных.
- **Без Jev Сёма работает ровно как до изменения.** Нет ключа, ключ
  отозван, кончились деньги, исчерпан бюджет, провайдер молчит — работа не
  ждёт, не откладывается и не падает (решение 9).

**Non-Goals:**
- Разгружать Pi на закрытых ящиках: туда решающая модель не попадёт, и
  обходить это нельзя.
- Решающая модель в суде моделей (арбитр, судья), в извлечении сроков и
  сумм, в переводе, в разборе памяти. Там нужен текст или устойчивость к
  чужому тексту.
- Примитив модулей `sema.decide` — потом, поверх того же вызова.
- Автоматический перенос писем в спам и любые действия в Telegram без
  кнопки человека.
- Выбор модели для фоновых ролей и модулей: только чат.
- MAX на первом шаге: спам в чатах начинается с Telegram.

## Decisions

### 1. Свой интерфейс `llm.Decider`, а не провайдер за `Complete`

```
type Question struct { ID, Kind, Instructions string; Options []Option } // Kind: choice | score | yesno
type Option   struct { Name, Desc string }
type Answer   struct { ID, Pick string; P, Confidence float64; Probs map[string]float64 }
Decide(ctx, state string, qs []Question) ([]Answer, error)
```

Почему: варианты выбора — часть запроса. Через строку `Complete` их пришлось
бы зашивать в формат промпта, а человек мог бы поставить Jev на роль
«Чаты», где он не ответит ни словом. Для `yesno` ответ сводится к той же
форме: `Pick` = «да» или «нет», `P` = вероятность выбранного, `Confidence` =
|2p − 1|. Тогда пороги у всех трёх видов означают одно и то же.

Альтернатива — провайдер за `Complete`, отдающий JSON строкой. Отвергнута
по двум причинам: формат вопроса превращается в мини-язык внутри промпта, а
у роли появляется модель, которая на половине мест не работает.

### 2. Решение идёт через `gate`

У `gate` метод `Decide` объявлен всегда. Если обёрнутый провайдер решать не
умеет, метод отвечает `llm.ErrNoDecide` — как `CompleteImage` с
`llm.ErrNoImages`. `BeforeModel` получает `state` вместе с текстом вопросов:
класс и согласие проверяются так же, как у обычного вызова. Провайдер
отчитывается через `llm.Report` с видом `decide`, дальше `OnCall` → журнал
расхода и «Что ушло наружу», бюджеты (`budgetCheck`) — без новых путей.
`TestNoFourthGate` дополняется: решение мимо `provider()` не строится.

Цена записывается строкой модели «$0.042 / $0 / 1M». Сейчас `parsePrices`
читает нулевую вторую цену как «та же, что вход» — её надо научить
принимать явный ноль.

### 3. Одна служебная роль «Решения»

Новая роль в `roleNames` / `roleDefaults`, в её списке — только модели с
умением «решает» (`ModelConf.Decides`, как «слышащие» у речи). Запасной
модели у роли нет: если решающая модель молчит, работает нынешний путь, а
не другая решающая. Передышка роли (`countRoleFail`, `roles.rest_min`)
действует как у всех ролей.

Альтернатива — своя модель у каждого применения. Отвергнута: модель одна, а
три выбора на экране дают три места, где можно ошибиться.

### 4. Режим каждого применения: «выключено · тень · включено»

Настройки в реестре (`engine/setting_defs.go`): `decide.mail_spam`,
`decide.chat_spam`, `decide.route`, по умолчанию «выключено». В тени
решающая модель зовётся, её ответ пишется в журнал решений, но решение
остаётся прежним. Включает применение человек, посмотрев отчёт.

**Журнал решений** — своя таблица `decision_log`: применение, объект (письмо,
сообщение, чат), модель, вариант, `P`, `Confidence`, время ответа, токены,
решение нынешнего пути и позже исход от человека. Срок хранения —
`decide.keep_days`. Журнал расхода для этого не годится: он про деньги, а
отчёту нужно соединить ответ модели с тем, что потом решил человек.

**Отчёт** по каждому применению за выбранные дни:
- сколько объектов дошло до решающей модели и сколько отвела дверь;
- совпадение с нынешним путём и с человеком;
- точность в трёх корзинах уверенности: выше верхнего порога, между
  порогами, ниже нижнего — это проверка калибровки;
- цена за день и время ответа.

### 5. Спам писем: решающая модель перед `classify`

```
письмо --> matchRule --> ragDecide --> filterModel
                                          |
                    закрытый ящик / секретное ----> нынешний путь (qwen3 на Pi)
                                          |
                                 открытый, обычное
                                          v
                              Decide(yesno "спам?")
                                          |
          P(спам) >= decide.mail_spam.high --> "ждёт решения" (как сейчас)
          P(спам) <= decide.mail_spam.low  --> проверенное, модель роли не зовём
          между порогами / ошибка / тень     --> нынешний classify
```

В `state` уходят отправитель, тема и выдержка — то же, что сегодня получает
`classify` — и примеры из `ragExamples`. Варианта «перенести в спам сам» у
решающей модели нет: подозрительное по-прежнему ждёт кнопки, а сам переносит
только `ragDecide` по подтверждённым правилам. Повторный разбор
(`rejudge.go`) идёт тем же путём. Уверенность, записанная в
`messages.confidence`, наконец значит то, что показывает бейдж.

Пороги по умолчанию — 0,9 и 0,1. Числа берутся из документации («ниже
0,6 — человеку», «для разрушительного — выше 0,9»), а настоящие значения
даст отчёт тени.

### 6. Спам в чатах: пометка после архива, до «ждёт ответа» и автоответа

Проверка стоит в `onTGMessage` **после** `AddTGMessage`: архив пишется
всегда, ничего не теряется. Проверяется только входящее не от владельца,
не в админ-чате и только в видах чатов из настройки `chat_spam.kinds`
(по умолчанию — комментарии каналов; дальше группы и личные — значением
настройки, без правки кода). Ответ решающей модели ждётся не дольше
`chat_spam.timeout_ms`; ошибка или тайм-аут — сообщение не помечено, и
всё идёт как сейчас.

Помеченное спамом:
- лежит в ленте свёрнутым («Похоже на спам · показать»);
- не зажигает «Ждут ответа»;
- не получает автоответа;
- не идёт в контекст чата и в почтовые правила уведомлений.

Действия человека:
- «Не спам» — снимает пометку и запоминает автора как своего;
- «Удалить в Telegram» и «Заблокировать автора» — действия наружу: только
  кнопкой, с `Confirm`, и только там, где у учётки есть права.

Решение человека по автору ложится правилом (учётка, автор → спамер или
свой). Следующие сообщения этого автора решаются правилом без вызова модели
— как `matchRule` у писем.

Ответ «не спам» ничего не разрешает: Jev не считает вход враждебным, и
бот, написавший «это не спам», добьётся только того, что его сообщение
останется на виду. Это нынешнее положение дел, хуже оно не становится.

### 7. Выбор модели: маршрут по вопросу, контекст — по выбору

```
вопрос человека (+ хвост route.tail реплик)
        |
        v
 gate: класс вопроса ---- секретное / тень / выключено ----> основная модель
        |
        v
 Decide(choice по таблице route_rules)
        |
        +-- Confidence < route.min ----------------------> основная
        +-- категория "только основная" -----------------> основная
        +-- категория -> модель M
                 |
                 v
        контекст собирается для основной;
        если для M outsideCut что-то вырезал бы ---------> основная
                 |
                 v
              ответ M  (ошибка M -> основная -> запасная)
```

- **Решающая модель видит только вопрос**, а не собранный промпт: письма и
  память ей не нужны, и отдавать их незачем. Маршрут решается в точке
  входа чата (`ChatReply`, `SendMessageTo`) до сборки контекста.
- **Таблица `route_rules`** в базе: категория, описание для решающей модели,
  модель (или «основная модель роли»), признак «только основная». Первичное
  заполнение: «болтовня» и «вопрос по данным» — дешёвая модель;
  «поручение», «код и модули», «серверы» — только основная. Правится на
  экране, кода не трогает. Первым вариантом в списке для решающей модели
  стоит «только основная»: Jev тянется к первому варианту, и ошибка тогда
  стоит денег, а не качества.
- **Дешёвая модель не видит меньше основной.** Контекст собирается для
  основной. Если по доверию дешёвой модели `outsideCut` что-то вырезал бы,
  вопрос уходит основной. Так маршрут не делает ответ хуже из-за закрытых
  ящиков. `chatCloud` для самой основной не меняется.
- **Блоки действий из ответа дешёвой модели не исполняются.** Если в ответе
  `sema-ssh`, `sema-module`, `sema-mcp` или `sema-skill`, ответ отбрасывается,
  и вопрос переспрашивается основной. Двойная цена платится только при
  ошибке маршрута, а команды предлагает только та модель, которой их
  доверили.
- **В ответе видно, кто отвечал**, как у запасной модели («Last» роли и
  подпись ответа). Кнопка «Ответить сильной моделью» — по макету.

Альтернатива — третья модель у роли («простая») вместо таблицы. Отвергнута:
категорий больше двух, и «серверы никогда не дешёвой» — это правило
категории, а не модели.

### 8. Провайдер TypeSafe

`internal/llm/typesafe.go` на стандартной библиотеке, как `perplexity.go`.
Пресет в справочнике провайдеров (`providers.go`, досыпка по
`providers.seed`): ключ — секрет `model:typesafe`, модель `jev-latest`,
источник цены `none`, цена — строкой модели. Адрес не нужен: `AddModel` не
требует его у этого вида. 429 и 529 повторяются с растущей паузой в пределах
тайм-аута роли. Вопросы одного объекта идут одним запросом: `state`
оплачивается один раз.

### 9. Нет Jev — Сёма работает как раньше

Решающая модель — помощь, а не ступень пути: ни одна работа её не ждёт и
не падает из-за неё. `Engine.decide` ошибку наружу не отдаёт. Вызывающий
получает «решения нет» и в той же работе идёт нынешним путём: без
отложенной попытки в очереди (`errPostpone` не возникает), без
«застряло», без красного «Здоровья».

| Что случилось | Что делает Сёма |
|---|---|
| Провайдер не подключён, ключа нет, на роли «Решения» стоит «нет» | Решающую модель не зовёт вовсе. «Тень» и «включено» ведут себя как «выключено»; на экране роли строка «нет модели — работаю как раньше». Уведомлений нет: это не беда, а выбор |
| 401 / 403 — ключ не подошёл или отозван | Роль «Решения» уходит на передышку **до смены ключа**, а не на `roles.rest_min`. Одно уведомление `decide:key` с переходом на экран провайдера |
| Кончились деньги на счёте TypeSafe (в документации код не назван — распознаём 402 и слова об оплате в теле ответа) | Та же передышка до смены ключа или ручного «Пробовать снова». Одно уведомление `decide:balance` |
| Исчерпан бюджет Сёмы (`budgetCheck`) | У решения свой потребитель `core:decide` (`llm.WithConsumer`). Отказ бюджета значит «решения нет», а не отказ работы, и пауза бюджета не выключает задачу, внутри которой шло решение: разбор почты, чтение Telegram, чат |
| 429 / 529, сеть, тайм-аут, ответ непонятной формы | Для этого объекта — нынешний путь. Три подряд — обычная передышка роли (`countRoleFail`) с её уведомлением. Строка в журнале решений с пометкой «не ответил» |

- **Передышка проверяется до вызова** (`roleCooldown`): пока роль отдыхает,
  лишнего сетевого круга нет вовсе, и письмо или сообщение не ждёт
  тайм-аута.
- **Тайм-аут у решения свой и короткий** — `decide.timeout_ms` в реестре, а
  не тайм-аут роли «Фильтр писем». Письмо не должно ждать минуту ради
  ответа, который приходит за десятую долю секунды.
- **Возврат сам по себе.** Ключ сменили, деньги внесли, нажали «Пробовать
  снова» — передышка снимается, уведомление закрывается по ключу
  (`CloseNotification`), применения продолжают в своём режиме.
- **Держит тест.** Провайдер не подключён, 401, 402, исчерпанный бюджет,
  тайм-аут. В каждом случае письмо размечается нынешним путём, сообщение
  Telegram ложится в ленту и получает автоответ, где он разрешён, чат
  отвечает основной моделью. Результат тот же, что без изменения, и время
  не больше тайм-аута решения.

### 10. Сначала макет

Экранов четыре: роль «Решения» с отчётом тени и режимами применений;
пороги на «Почта → Спам»; виды чатов на «Telegram → Ответы и пределы»;
таблица `route_rules` на «Модели и роли». По правилу проекта макет
(`design/`) идёт до кода экранов. Движок, журнал решений и тень от макета
не зависят.

## Risks / Trade-offs

- [Русский у Jev хуже английского, цифр нет] → тень на живом потоке,
  каждое применение включается отдельно, отчёт по корзинам уверенности.
- [«Калиброванная» уверенность — слова продавца] → отчёт меряет точность в
  каждой корзине; пороги — настройки, а не числа в коде.
- [Инъекция сдвигает ответ решающей модели] → ни одно её решение ничего не
  разрешает. «Не спам» — статус-кво. Маршрут не открывает модели больше,
  чем открыла бы основная. Блоки действий дешёвой модели не исполняются.
- [Тянется к первому варианту] → первым ставится вариант, ошибка которого
  дешевле: «только основная» в маршруте, у спама вопрос «да / нет», а не
  список.
- [Новый провайдер в США, режим без хранения только для enterprise] → до
  подключения провайдера человеком ничего не уходит. Каждая отправка — в
  «Что ушло наружу». Закрытое и секретное отводит `gate`.
- [Провайдер ранний, API может смениться] → провайдер заперт в одном файле
  `internal/llm`. Режим «выключено» возвращает всё на нынешний путь.
- [Лишний сетевой круг в почте и в чате] → короткие тайм-ауты, при ошибке —
  нынешний путь. Передышка роли «Решения» не даёт ждать молчащую модель
  каждый раз.
- [Нет ключа, кончились деньги на счёте TypeSafe или бюджет Сёмы] →
  решение 9: решения нет, работа идёт нынешним путём, одно уведомление,
  возврат сам после смены ключа или оплаты.
- [Маршрут экономит мало, если основная модель и так дешёвая] → это
  покажет тень: в отчёте цена «как было» против «как было бы».

## Migration Plan

1. Миграции: таблицы `decision_log`, `route_rules` (с первичным
   заполнением), правила авторов чатов, пометка спама у сообщений
   мессенджеров. Новые настройки — в реестре; все режимы «выключено».
2. Выкат ничего не меняет, пока человек не подключит провайдера TypeSafe
   и не назначит модель на роль «Решения».
3. Порядок включения: тень спама писем → неделя отчёта → «включено»; тень
   спама в чатах (комментарии) → отчёт → «включено»; тень маршрута → отчёт
   → решение владельца.
4. Откат — режим «выключено» у применения. Журнал решений и правила
   остаются: они ничего не делают без режима.

## Open Questions

- Какая модель стоит основной у «Чатов» и есть ли что экономить — ответ
  даст тень маршрута, устройство от этого не меняется.
- Проверять ли спам в группах и личных чатах, а не только в комментариях
  каналов, — значение настройки `chat_spam.kinds` после отчёта по
  комментариям.
- Готов ли владелец отдавать тему и начало писем открытых ящиков ещё
  одному провайдеру в США — до подключения провайдера ничего не уходит,
  поэтому решается при подключении.
- Пороги по умолчанию (0,9 / 0,1 у спама, `route.min`) — после отчёта тени.
