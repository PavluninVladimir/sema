## Context

Сейчас человека ждут в четырёх местах: `ssh_pending` («Серверы»),
`pendingModule`/`pendingGrants` («Модули», в памяти сервера),
`pendingSkills` (карточки чата, в памяти), коллекция `items` модуля
«Требует внимания» (`module_data`). Отчёт модуля `watch` («Присмотр за серверами»)
— текст в чате «Серверы», модель получает целиком `/log print` (22 тыс.
токенов за вызов). Макет: `design/Notifications.dc.html`.

## Goals / Non-Goals

**Goals:**
- Одна таблица и одна форма для всего, что ждёт человека; экран с
  фильтром-чипами; счётчик в меню; сводка на «Почте».
- `Engine.Notify` для ядра, `sema.notify` / `sema.remind` для модулей.
- Почтовые правила в ядре, задача «Сроки» в ядре, модуль attention удалён с
  переносом данных.
- Модуль серверов заполняет поля, а не пишет текст; модель получает
  выжимку, а не сырой журнал.

**Non-Goals:**
- Сами модули-каналы (Telegram, Matrix, ntfy) — не в этом изменении:
  здесь только право `notify_channel` и вызов `deliver(n)`; первый такой
  модуль Сёма напишет по просьбе в чате.
- Переделка экрана «Серверы»: он остаётся зеркалом ожидающих команд.

## Decisions

- **Ключ заменяет, история остаётся.** `notifications.key` уникален среди
  открытых: новая запись с тем же ключом переводит старую в `replaced`.
  Так отчёт о сервере всегда один, а «Сделано» хранит вчерашние.
- **Действия — JSON с видами.** `{kind: "ssh", host, cmd, label}`,
  `{kind: "goto", screen}`, `{kind: "module", module, fn, arg}`,
  `{kind: "done"}`, `{kind: "dismiss"}`, `{kind: "core", op: "approve_ssh"
  | "grant_module" | "decide_skill" | "accept_fp", ref}`. Кнопка на экране
  зовёт одно действие DSL `notify_act` с целью `<id>~<номер действия>`;
  сервер исполняет по виду и переводит запись в `done`. Команда `ssh` от
  модуля проверяется по `GrantedHosts` при записи, а не при нажатии.
- **Запросы ядра пишутся в момент рождения.** `AddSSHPending` →
  `Notify(core, key ssh:<id>)`; `askGrants` → `Notify(core, key
  grants:<модуль>)` с действиями «Выдать всё» / «Открыть модуль»;
  `findSkillBlocks` → `Notify(core, key skill:<id>)`; смена отпечатка →
  `Notify(core, key fp:<сервер>)`. Решение в старом месте («Серверы»,
  «Модули», карточка чата) закрывает и уведомление по ключу — источник
  правды один.
- **Почтовые правила — таблица `notify_rules`** с теми же полями, что у
  `rules` модуля (id, title, cond, kind, days, mode, sort, enabled),
  первичное заполнение — из `SEED_RULES` attention.js. Применение — в
  `emitModuleEvent` для `message.added` (ядро само, без очереди модулей):
  `applyMailRules(msg)`. «Сроки» — воркер ядра раз в час: `remindAt <= now`
  → уровень `alert`, чат «Уведомления» получает строку.
- **Перенос данных.** Миграция при старте: если есть `module_data` модуля
  attention — `items` → `notifications` (state waiting→open, done→done,
  dismissed→dismissed; key `mail:<msg>` или `reminder:<id>`), `rules` →
  `notify_rules`; модуль удаляется из `modules.json`, файл `attention.js`
  из сборки убирается. Инструмент `attention.remind` остаётся синонимом
  `sema.remind` в реестре скриптов (одно изменение).
- **Модуль серверов.** Скиллы получают раздел «Ответ модели — JSON»:
  `{level, summary, fields: [...], actions: [...]}`; модуль зовёт
  `sema.llm` с выжимкой (журнал MikroTik — последние 60 строк с
  `error|warning|critical|login`), разбирает JSON и кладёт `sema.notify`.
  Переписывает Сёма из чата по обновлённому скиллу — это и проверка, что
  форма понятна модели.
- **Каналы.** `notify_channels` (kind, title, enabled, min_level, sources,
  quiet_from, quiet_to, config JSON). Доставка — из `Notify` сразу после
  записи, по каждому включённому каналу: `mac` — ничего не шлёт, запись
  попадает в ленту `/api/notifications/feed?since=<id>` (клиент опрашивает
  раз в 5 с вместе с экраном и показывает `UNUserNotificationCenter`;
  нажатие — `$goto notifications@<id>`), `mail` — письмо через `mail.Send`
  из ящика с исходящей почтой (сводка по расписанию задачи ядра
  «Сводка уведомлений» или тревога сразу), `module:<имя>` — вызов
  `deliver(n)` модуля с правом `notify_channel`. Тихие часы — отложенная
  доставка: поле `deliver_after`, воркер «Сроки» досылает. Доставки
  пишутся в `notify_log` (уведомление, канал, время, ошибка).
- **Клиент.** `NotifyBridge.swift`: запрос разрешения при первом включении
  канала Mac, опрос ленты, показ с заголовком и строкой-итогом, действие по
  нажатию через `AppState.select(screen:)`. Порог и источники — на сервере,
  клиент ничего не решает.
- **Фильтр — вкладки DSL.** Чипы — `doc.Tabs` с идентификаторами
  `notifications`, `notifications@servers`, `@mail`, `@requests`, `@done`;
  без поля поиска (`Searchable: false`).

## Risks / Trade-offs

- Два места правды на переходный период (ssh_pending и уведомление): решает
  ключ и закрытие по ключу из обоих мест.
- Миграция `module_data` attention: делается один раз, старые данные не
  удаляются до следующего изменения — можно вернуть.
- Модель может не удержать JSON-форму: разбор терпимый (`extractJSON`),
  при провале уведомление уровня `warn` «отчёт не разобран» с сырым
  текстом в поле, чтобы ничего не терялось.
