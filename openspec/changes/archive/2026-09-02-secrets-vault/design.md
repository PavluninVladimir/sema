## Context

Секреты уже шифруются одним слоем (`enc:v1`, ключ из окружения), но живут
по разным местам внутри настроек ящиков и моделей; память скриптов
(`store.set`) хранится открытой. Модель прав модулей есть и работает по
примитивам ядра. SSH-примитива пока нет — хранилище готовит для него почву.
Мотивация — см. proposal.md.

## Goals / Non-Goals

**Goals:**

- Один список всех секретов системы с тем, кто их использует.
- Секрет попадает к модулю только по имени и только после подтверждения.
- Приватный ключ SSH нельзя утянуть даже с правами модуля.

**Non-Goals:**

- Менеджер паролей для человека (автозаполнение, браузер) — другой продукт.
- Перенос ключей моделей и паролей ящиков в новую таблицу: они остаются у
  владельцев и лишь показываются в витрине.
- Синхронизация хранилища между машинами.

## Decisions

### Хранилище — примитив ядра с правами поимённо

В манифесте модуля появляется `secrets: ["gitlab-token", "ssh:prod-1"]`.
Право `secrets` без имён не существует. В песочницу модуля кладётся функция
`sema.secret(name)`, которая знает только выданные имена; про остальные она
отвечает одинаково «не выдан», не раскрывая, есть ли такой секрет.

*Альтернатива:* общее право «секреты» как у почты или сети — отклонено:
модуль, написанный моделью, унёс бы всё разом.

### SSH-ключ генерируется внутри, ed25519, чистый Go

`golang.org/x/crypto/ssh` умеет ed25519 без cgo: кросс-компиляция под Pi и
VPS сохраняется. Приватная часть шифруется как секрет и не имеет пути наружу
ни через экран, ни через API, ни через модуль — примитив `ssh` будет брать её
из хранилища сам, по имени. Импорт чужого ключа допускается с предупреждением.

*Альтернатива:* просить человека загрузить `~/.ssh/id_rsa` — отклонено:
личный ключ человека не должен жить в базе приложения.

### Журнал использования — таблица, а не строка «последний раз»

Каждое обращение: секрет, кто (модуль, задача, примитив), когда, выдан или
отказано. В списке видно последнее, по клику — история. Это единственный
способ заметить модуль, который лезет не за своим.

### Память скриптов шифруется целиком

Ключи `script.*` идут через тот же слой. Ценой становится чтение с
расшифровкой на каждый `store.get`; память скриптов маленькая, это дёшево.
Запрещать класть туда секреты и надеяться — не вариант.

*Принято как допущение:* владелец не ответил на этот вопрос прямо; решение
взято как более надёжное и легко откатывается.

### Скрипты из чата секретов не получают

Скрипт, написанный моделью по ходу разговора, выполняется с встроенными
инструментами, но без `sema.secret`. Нужен секрет — Сёма предлагает оформить
модуль, где права подтверждаются человеком.

### Пароли к серверам разрешены, но с честной пометкой

Вид «пароль» существует и для серверов (не только ящиков), при этом форма
подсказывает, что ключ надёжнее и Сёма может его сгенерировать.

### Витрина — продолжение «Безопасности»

Экран «Ключи и секреты» показывает свои записи и чужие (ящики, модели, токен
почты) одним списком с пометкой «используется: …». Значение нигде не
показывается; действия — заменить, отозвать, удалить, посмотреть журнал.

## Risks / Trade-offs

- **Имя секрета — часть договора между модулем и человеком.** Переименовали
  секрет — модуль его потеряет; в форме переименования надо показывать, кто
  на него ссылается.
- **Журнал растёт.** Обращения по расписанию каждые 30 минут дадут тысячи
  строк; хранить последние N на секрет, старое сворачивать в счётчик.
- **Секрет в памяти процесса.** Как и ключ шифрования, значение секрета в
  момент использования есть в памяти сервера; от root на машине это не
  защищает — и об этом сказано на экране «Безопасность».
- **Публичный ключ надо самому донести на сервер.** Сёма не может добавить
  его туда сам без другого доступа; на первом шаге это ручное действие с
  подсказкой.
