## Context

Мотивация — в `proposal.md`.

**Как Сёма устроена сегодня.** Файл запуска несёт адрес, каталог данных и имя
переменной с ключом (`internal/config/config.go:113-124`); остальное живёт в
базе. Умолчания: `127.0.0.1:8765`, каталог `"."`, ключ из `SEMA_KEY`
(`config.go:148-155`), перекрытие — флаг, затем переменная (`applyEnv`,
`config.go:178-190`). Старт: каталог → база → движок → слушатели → HTTP
(`cmd/sema/main.go:45-105`). Сигнал ловится (`main.go:86`), но базу никто не
закрывает штатно и checkpoint не делает.

**Что уже правильно в compose.** `server/docker-compose.yml` держит
именованный том (не bind-mount: через границу виртуальной машины на маке не
работают блокировки SQLite, и база уже была повреждена), порт только на
`127.0.0.1`, healthcheck и — важное — **ключ в `.env`, а не в томе**, с
комментарием «иначе резервная копия тома унесёт и базу, и ключ к ней». Это
правило принято; его надо распространить, а не изобрести.

**Что есть в образе.** `Dockerfile` ставит `poppler-utils` (`pdftotext`,
`pdftoppm`), `tesseract-ocr` с русским и английским, `ca-certificates`,
`tzdata`, `sqlite`. То есть весь разбор содержимого уже одинаков на всех
целях — это и есть главный выигрыш решения «Docker везде».

**Чего нет.** Замка единственного экземпляра. Штатной остановки. Ротации
журнала. Резервной копии. Самоосмотра. Установщика.

## Goals / Non-Goals

**Goals:**

- Одна цель установки вместо пяти разных историй.
- Установка и удаление на Windows — одним действием.
- Ничего не теряется при обновлении, остановке и переезде.
- Всё, что зависит от системы, — в одном месте.

**Non-Goals:**

- Настольные оболочки, нативные клиенты, службы systemd и launchd
  (решение 3).
- Нативный запуск сервера как поддерживаемая установка: он остаётся режимом
  разработки и в целях установки не числится.
- Оркестрация, кластер, несколько хозяев на одну базу.
- Обратные миграции схемы (решение 8).
- Автообновление на месте.

## Decisions

### 1. Docker — единственный хозяин, на всех целях

| Цель | Роль | Чем поднимается | Каталог данных |
|---|---|---|---|
| Windows | хозяин | `sema-setup.exe`, дальше compose | том `sema-data` → `/data` |
| mac | хозяин | `docker compose up -d` | том `sema-data` → `/data` |
| Linux-VPS | хозяин | `docker compose up -d` | том `sema-data` → `/data` |
| Raspberry Pi | хозяин | `docker compose up -d` | том `sema-data` → `/data` |
| Браузер, телефон | тонкий вход | адрес сервера | нет |
| `Sema.app` | тонкий вход | приложение | нет |

Внутри контейнера каталог данных всегда `/data` — то есть на **всех** целях
установки вопрос «где данные» не стоит вовсе.

**Нативного запуска в этом списке нет, и это не описка.** Собранный
`./sema-server` на маке — способ разработки, а не установка: им не
пользуются как Сёмой, ему не обещают ни автозапуска, ни резервных копий, ни
переезда. Поэтому умолчание каталога данных для него **не трогаем**: оно
остаётся `"."` (`config.go:152`), как сегодня, вместе с рабочим каталогом
разработчика. Менять его на XDG значило бы завести миграцию и риск потерять
данные ради режима, который целью установки не является.

**Правило: один хозяин на каталог данных**, а не на машину. Две Сёмы с
разными томами и разными портами законны; две на одном томе — нет. Замок
(решение 4) стережёт каталог.

Выигрыш решения, который стоит назвать: `pdftotext`, `tesseract` и часовые
пояса одинаковы везде, потому что это один образ. Вся ветка работы «чем
читать PDF и картинки на Windows» исчезает целиком.

Минус: между Сёмой и файлами человека появляется граница контейнера. Она
бьёт по наблюдаемым папкам (решение 6) и по обслуживанию: правило «к базе
снаружи не прикасаться» (оно записано в «Граблях» и куплено дорого —
повреждённой базой 3 сентября) означает, что привычное «открыть sqlite3 и
посмотреть» отменяется.

**Поэтому обслуживание становится набором команд Сёмы, а не походом внутрь
контейнера.** Человек не должен придумывать, как ему сделать копию или
починить базу:

| Задача | Чем делается |
|---|---|
| Резервная копия | `sema -backup` (решение 11) |
| «Не работает, почему» | `sema -doctor` (решение 13 спеки) |
| Посмотреть журнал | `docker compose logs` и файл журнала в томе |
| Восстановить | `sema -restore` с самоосмотром |
| Битая база | `-doctor` называет беду, `-restore` из копии; спасение
  `.recover` — последнее средство и описано отдельно |
| Заглянуть в данные | экспорт через `-backup`, а не sqlite3 по живому |

Правило простое: **любое обслуживание — команда, которую Сёма выполняет
сама**; открытая база снаружи остаётся запрещённой.

### 2. Docker Desktop — единственный поддержанный путь

**Выбран Docker Desktop.** Причины по убыванию: `compose` встроен и ведёт
себя ровно так, как наш файл; общий доступ к папкам настраивается в
интерфейсе; автозапуск при входе — тумблер; молчаливая установка через
`winget` проверена; на маке и Windows это одно и то же.

**Минусы называем прямо, их три.**

*Лицензия.* Docker Desktop бесплатен для личного использования, учёбы,
некоммерческого открытого кода и небольших компаний, но требует платной
подписки в крупных. Для Сёмы как личного ассистента это не помеха, но если
её однажды поставят на рабочий ноутбук большой компании — помеха сразу.

*WSL2.* Нужен в любом случае. Значит: Windows 10 версии
2004+ или 11, включённая виртуализация в BIOS, установка ядра WSL2, иногда
перезагрузка.

*Объём.* Docker Desktop — единицы гигабайт, плюс дистрибутив WSL2, плюс наш
образ (Alpine с poppler и tesseract с языковыми данными — заметно больше
голого сервера). Установка «на пару сотен мегабайт» не получится, и обещать
этого не будем.

**Podman как «запасной, но не поддерживаемый» — из документа убран.** В
прежней редакции он там был, и ревью право: это ложный путь. Либо мы
проверяем его в приёмке при каждой правке, либо не упоминаем как вариант —
третьего нет, потому что «попробуйте, но мы не обещаем» перекладывает нашу
неуверенность на человека.

Проверять два движка мы не будем. Значит **поддержан один: Docker Desktop**.
Случай «лицензия не подходит» остаётся **нерешённым, и мы это называем**:
такой человек сегодня Сёму поставить не может, и придумывать ему обходной
путь, который никто не проверял, нечестно. Появится необходимость — это
отдельная работа с отдельной приёмкой, а не сноска.

**«Одинаков на маке и Windows» — преувеличение, снимаю.** Compose и команды
действительно одни и те же, но нас касаются три различия:
*файлы* — проброшенная папка хозяина на Windows идёт через мост WSL2, на
маке через свой механизм, и обе медленнее родной файловой системы, но
по-разному и с разными правами; *владелец файлов* — uid внутри контейнера
сопоставляется хозяйским файлам на маке мягче, чем через мост Windows (отсюда
решение 6); *сеть* — имя хозяина доступно на обеих системах, но на Linux его
пришлось бы добавлять руками (нам это уже не нужно, см.
`models-over-network`). Одинаковы у них лицензия и автозапуск.

### 3. Служб под системы не будет — автозапуск даёт Docker, и у него есть границы

Прежняя редакция заводила `sema -install-service` под systemd и launchd. Это
уходит целиком.

Причина: контейнер уже умеет подниматься сам. `restart: unless-stopped` в
compose плюс автозапуск самого Docker при входе в систему дают ровно то, ради
чего заводилась служба. Писать unit-файлы под три системы, чтобы получить то,
что уже есть, — работа без результата.

**Автозапуск Docker Desktop — не служба, и разница существенная.** На VPS и
Pi демон Docker запускается системой, до и независимо от входа человека:
Сёма работает всегда. На маке и Windows Docker Desktop стартует **при входе
пользователя**, и отсюда список случаев, когда Сёма **не работает**, — его
надо сказать прямо, а не обнаружить потом:

- машина включена, но человек ещё не вошёл в систему (после перезагрузки до
  ввода пароля) — Сёмы нет;
- человек вышел из системы (не заблокировал экран, а именно вышел) — Сёмы
  нет;
- человек выключил автозапуск Docker Desktop или закрыл его — Сёмы нет;
- Windows перезагрузилась после обновления и ждёт входа — Сёмы нет.

Заблокированный экран при выполненном входе — работает. Спящий компьютер —
не работает, и это очевидно, но письма разберутся при пробуждении: очередь
для того и есть.

Кому нужна Сёма круглосуточно, тому нужен VPS или Pi, где Docker — системная
служба. Это честный ответ, а не отговорка: на ноутбуке круглосуточной Сёмы
не бывает ни с треем, ни со службой, потому что ноутбук закрывают.

**Продвинутый путь** (бинарник с systemd, без Docker) не поддерживается и не
описывается. Он возможен — сервер собирается статически, — но каждый
описанный путь надо проверять, а проверять мы будем один.

### 4. Замок сервера, до старта очередей

Сервер можно запустить и мимо compose — вторым контейнером, вручную,
`docker exec`. Тогда по одной базе идут два сердцебиения и две очереди:
работы задвоятся, письма разберутся дважды, счётчики расхода соврут.

**Замок берётся блокировкой средствами операционной системы** на файле в
каталоге данных (`flock` с `LOCK_EX|LOCK_NB`, на Windows `LockFileEx`), и
дескриптор держится всё время жизни процесса. Берётся **сразу после того,
как каталог известен, и до `engine.New`** (`main.go:81`).

Прежняя редакция описывала замок по номеру процесса: «занят живым — не
поднимаемся, занят мёртвым — забираем». **Это было неверно, и для Docker
особенно.** Номера процессов внутри контейнера свои: в контейнере Сёма почти
всегда процесс номер 1, и проверить «жив ли процесс 1» из другого контейнера
невозможно — там свой процесс 1. Ещё хуже, что решение по номеру
противоречит самой блокировке: ОС уже знает правду, а мы поверх неё
угадываем.

Блокировка ОС снимает это целиком: ядро освобождает её само, когда процесс
умирает любым способом — штатно, `SIGKILL`, `docker kill`, падение хоста.
Никакой логики «забрать у мёртвого» не нужно, и флаг принудительного снятия
тоже не нужен — его в прежней редакции пришлось выдумывать ровно из-за
неверной модели. Два контейнера на одном томе видят один и тот же файл на
одном ядре, поэтому блокировка работает и между ними.

Рядом с файлом замка лежит **диагностическая запись** — кто взял, когда, имя
хозяина и идентификатор контейнера. Она ни на что не влияет и нужна только
для того, чтобы человеку было что показать: «занято вот этим». Решения по
ней не принимаются никогда.

**Порядок старта фиксируется, потому что сегодня он неверен**: каталог
создаётся, база открывается и мигрирует, и только потом что-либо
проверяется. Правильно, до любого побочного действия:

1. определить каталог данных;
2. создать и проверить запись;
3. **взять замок**;
4. открыть журнал;
5. открыть базу и провести миграции;
6. поднять движок, очереди, сердцебиение;
7. поднять HTTP и слушатели.

Занят живым процессом — не поднимаемся, называем процесс. Занят мёртвым —
забираем и пишем в журнал, что прошлая остановка была нештатной.

**Где замок работает.** Поддержаны ровно два случая: локальный диск и
именованный том Docker. Всё остальное — не поддержано.

Определять файловую систему «на глаз» мы не будем: это ненадёжно и
нереализуемо переносимо. Вместо этого при старте делается **проба
блокировки**: взять блокировку, попробовать из этого же процесса взять её
вторым дескриптором и убедиться, что вторая попытка отклонена. Ведёт себя
не так, как должно (обе удались, или операция не поддержана) — Сёма не
поднимается и говорит прямо: на этой файловой системе замок не работает,
каталог данных нужно перенести на локальный диск или в том Docker.

Так мы проверяем не название файловой системы, а именно то свойство, ради
которого замок и нужен.

### 5. Штатная остановка, сроки числами, инвариант очереди

**Порядок важен, и в прежней редакции он был неверен**: признак чистого
закрытия писался после закрытия базы, то есть писать его было уже некуда.
Правильно так:

1. записать в базу пометку «закрываюсь»;
2. перестать принимать запросы;
3. дать текущей работе доработать в пределах срока;
4. закрыть слушатели агентов и Telegram;
5. **последней транзакцией** записать «закрыт чисто»;
6. `PRAGMA wal_checkpoint(TRUNCATE)` и закрыть базу;
7. снять замок.

Признак живёт в базе и ставится, пока база ещё открыта. При старте он
читается и тут же сбрасывается в «работаю»: значит, увидев при следующем
запуске не «закрыт чисто», мы точно знаем, что прошлый выход был
неаккуратным.

**Сроки:** мягкий 30 секунд, жёсткий 120. Оба — настройки, но первичные
значения такие, и они же идут в `stop_grace_period: 150s` в compose. Это
важно: **по умолчанию Docker ждёт 10 секунд** и бьёт `SIGKILL` — то есть без
этой правки штатной остановки в контейнере не вышло бы, даже будь она
написана.

**Штатная остановка — не гарантия, и рассчитывать на неё нельзя.**
`wal_checkpoint(TRUNCATE)` на большой базе может не уложиться в срок; а
`docker kill`, выключение хозяина по питанию и падение процесса не дают
никакого срока вообще. Поэтому:

- checkpoint делается по возможности, со своим сроком; не успел — базу всё
  равно закрываем, журнал предзаписи остаётся, и это нормально: SQLite
  восстановит его при следующем открытии сам;
- **опорой служит не аккуратный выход, а поведение при следующем старте.**
  Увидели, что признака чистого закрытия нет: проводим проверку целостности,
  пишем в журнал, что прошлый выход был неаккуратным, и продолжаем работу.
  Никаких «этого не должно случиться» — случится обязательно.

**Одного замка мало — нужен инвариант очереди.** «Ничего не теряется»
держится не на аккуратном выключении, а на том, что переживает неаккуратное.
Общее для всех работ: работа, взятая в аренду (`work_queue`, аренда уже есть
в `store/queue.go`), по истечении срока возвращается в ожидание сама.

Дальше **работы делятся надвое, и обещать им одно и то же нельзя.**

*Внутренние работы* — те, чей результат целиком в нашей базе: разбор письма,
вектор, сведение памяти, пересчёт дайджеста. Для них завершение работы и
запись результата идут **одной транзакцией**, и повтор просто переделывает
то же самое. Обещание: **ровно один раз**.

*Внешние действия* — те, что меняют мир за пределами базы: письмо перенесено
на почтовом сервере, команда выполнена на сервере, комментарий отправлен в
трекер, деньги потрачены на вызов модели. Здесь транзакция бессильна: между
«сделали снаружи» и «записали у себя» всегда есть щель, и если упасть в ней,
повтор сделает действие второй раз.

Для них правило другое: **у действия есть ключ, признак «сделано снаружи»
записывается до фиксации результата, а перед повтором проверяется по внешнему
признаку — не сделано ли уже**. Перенос письма это уже умеет по своей природе
(идентичность письма — Message-ID, а не UID, и `Locate` проверяет результат).
Обещание честное: **не более одного раза для изменяющих** и **хотя бы один
раз для читающих**. Ровно одного раза с внешним миром не бывает ни у кого, и
делать вид, что у нас есть, мы не будем.

### 6. Наблюдаемые папки на Windows: только чтение, только из профиля

Сегодня папка хозяина пробрасывается как `~/Inbox:/data/inbox`. На Windows
это `C:\Users\…` через границу WSL2, и там всё иначе.

*Скорость.* Доступ к файлам Windows из контейнера идёт через мост и заметно
медленнее родной файловой системы. На папке в тысячи файлов это чувствуется.

*События.* Уведомления об изменениях через мост не приходят надёжно. Нам, похоже,
повезло: задача «Папки с файлами» (`foldersPass`) **опрашивает** папку раз в
минуту, первый уровень, до 50 файлов за проход, и помнит принятое в
`folder_seen` по пути, размеру и времени. Опрос устроен так, что события ему
не нужны.

Но **«похоже» — не «проверено», и обещать заранее нечего**: через мост WSL
иначе ведут себя и права, и скорость, и время изменения файла, на которое
опирается `folder_seen`. Поэтому это не вывод, а **гипотеза с пунктом
приёмки**: положить файл в наблюдаемую папку на живой Windows, убедиться,
что он принят один раз и не принимается повторно, и замерить проход по папке
в тысячу файлов. Не подтвердится — наблюдаемые папки на Windows
объявляются неподдержанными, и это честнее, чем тихо не работающая функция.

Причину, по которой здесь именно опрос, надо записать рядом с `foldersPass`:
иначе кто-нибудь однажды «оптимизирует» его на события и сломает Windows.

*Регистр.* Файловая система Windows не различает регистр, а ключи
`folder_seen` — различают. Один и тот же файл, увиденный как `Scan.pdf` и
`scan.PDF`, будет принят дважды. Сравнение путей для папок на таких
файловых системах — без учёта регистра.

*Длинные пути.* Путь длиннее 260 знаков через мост может не открыться. Это
не чиним: файл честно попадает в «не удалось прочитать» с причиной.

*Права.* Контейнер работает не от root (`USER sema`, uid 10001), а файлы с
той стороны моста приходят с чужим владельцем. Чтение обычно проходит,
запись — не всегда. Отсюда решение: **на Windows наблюдаемая папка работает
на чтение**, а настройка «удалять после приёма» для неё выключена и помечена
непроверенной. Обещать удаление файлов человека там, где мы не уверены в
правах, нельзя.

Требование к пути: папка лежит **внутри профиля пользователя** и открыта в
общем доступе Docker Desktop. Папки вне профиля и сетевые диски — не
поддержаны.

### 7. `sema-setup.exe` — порядок действий, а не приложение

Одна кнопка на Windows — это маленький консольный бинарник на Go. Не
клиент, не оболочка, не окно: он ничего не рисует, у него нет рендерера, и
третьим клиентом он не является. Порядок:

1. проверить, есть ли рабочий Docker (`docker version`);
2. нет — поставить молча:
   `winget install --id Docker.DockerDesktop --exact --silent --accept-package-agreements --accept-source-agreements`;
3. дождаться готовности демона (Docker Desktop поднимается не мгновенно);
4. создать том и записать `compose.yml` рядом с собой;
5. сгенерировать ключ, записать `.env` **вне тома**, права — только владельцу;
6. скачать образ закреплённой версии;
7. `docker compose up -d`;
8. дождаться **готовности**, а не просто ответа (см. решение 8а);
9. открыть браузер на `http://127.0.0.1:8765`;
10. показать фразу восстановления и потребовать подтвердить, что сохранена.

**Что пойдёт не так и что человек увидит.** Это половина работы, а не
дополнение к ней:

| Беда | Что делает установщик | Что видит человек |
|---|---|
| Нет `winget` (Windows 10 до 1809 или без App Installer) | останавливается, ждёт, проверяет снова | «Не нашёл winget. Поставьте App Installer из Microsoft Store или Docker Desktop вручную — вот ссылка» |
| Нет прав администратора | не пытается ставить молча | «Установка Docker требует прав администратора. Запустите этот файл от имени администратора или попросите администратора поставить Docker Desktop» |
| Виртуализация выключена в BIOS | распознаёт этот случай по ответу Docker, а не отдаёт общую ошибку | «Docker не может запуститься: выключена виртуализация. Включите Intel VT-x / AMD-V в BIOS» |
| WSL2 не установлен | ждёт, пока Docker Desktop поставит сам | не смог — «Выполните `wsl --install` и перезагрузитесь, потом запустите этот файл снова» |
| Docker Desktop требует перезагрузки | останавливается, ничего не откатывая; запоминает, на каком шаге стоял | «Docker установлен, нужна перезагрузка. Перезагрузитесь и запустите этот файл снова — он продолжит с этого места» |
| Политика домена запрещает установку | не обходит политику никакими путями | «Установка запрещена политикой организации. Docker Desktop должен поставить администратор» |
| Порт 8765 занят | не занимает другой порт молча | называет, кто держит порт, и предлагает выбрать другой (решение 9) |
| Нет сети | повторяет скачивание, ничего не ломая | «Не удалось скачать образ, пробую снова» |
| Демон не поднялся за отведённое время | не считает это успехом | «Docker установлен, но не запустился. Откройте Docker Desktop вручную и запустите этот файл снова» |

Правило для всех случаев: установщик **ничего не делает наполовину**. Не
получилось — говорит, что именно, и как это чинится; уже созданное (том,
`.env`) остаётся, и повторный запуск продолжает с того места, а не начинает
заново и не перезаписывает ключ.

**Цена: 3–5 дней**, из них большая часть — не основной путь, а вот эта
таблица и её проверка на чистой виртуалке.

**Обновление и удаление — тем же файлом.** `sema-setup.exe update`: снять
резервную копию (обязательно), `compose pull`, `compose up -d`.
`sema-setup.exe remove` разделён надвое, и это не формальность.

**«Убрать Сёму»** (по умолчанию): штатная остановка, удаление контейнера,
`.env`, ярлыка и автозапуска. **Том с данными остаётся нетронутым.** Повторная
установка подхватывает его и продолжает с теми же письмами и настройками.

**«Убрать данные»** — отдельное действие, требующее **ввести слово
подтверждения**, а не нажать «да». Перед этим Сёма показывает, что именно
исчезнет: сколько писем, файлов, чатов, и что без резервной копии это
необратимо. Галочки и умолчания здесь недопустимы: том с многолетней
перепиской не должен удаляться потому, что человек привычно нажал Enter.

Предложение снять копию делается прямо здесь, до удаления.

**На других целях установщика нет.** На маке, VPS и Pi человек и так живёт в
терминале, а Docker у него стоит: там установка — это `docker compose up -d`
рядом с `compose.yml` и `.env`. Одна схема, одно исключение: Windows, где
Docker не предустановлен и терминал непривычен.

### 8. Обновление: закреплённый тег, копия до, откат только копией

Тег в compose — **неизменяемый**: `sema:1.4.2`, который никогда не
перезаписывается. Не `latest` (лотерея: неизвестно, что приедет) и не
календарный тег, который потом перезаливают, — тогда «та же версия» перестаёт
быть той же. Рядом с тегом записывается **отпечаток образа**, и именно он
делает версию точной: тег можно случайно перезалить, отпечаток — нет.

**Что считается предыдущей версией.** Не «та, что была в реестре до», а та,
что работала у этого человека. Перед обновлением установщик сохраняет рядом
прежние тег и отпечаток (`sema.prev`), и откат — это они плюс копия, снятая
тем же шагом. Иначе «откатиться» превращается в угадывание.

**Как обновляется сам файл compose.** Он у человека на диске и со временем
расходится с тем, что ожидает новая версия (появился `stop_grace_period`,
исчез `SEMA_HOST_ALIAS`). Поэтому: `compose.yml` считается **файлом,
которым владеет установщик** — при обновлении он перезаписывается из шаблона
новой версии, а прежний сохраняется рядом. Правки человека живут в
`compose.override.yml`, который установщик **не трогает никогда**: там
проброшенные папки, свой порт, свои переменные. Так обновление приносит
новые настройки, не затирая чужого.

Порядок: `sema -backup` (**обязательный шаг**) → `compose pull` →
`compose up -d` → штатная остановка прежнего → миграции в новом.

**Про откат честно: обратных миграций нет и не будет** — это отдельная
дисциплина, которую не тянет проект такого размера. Значит откат на прежний
образ возможен **только вместе с восстановлением копии**, снятой до
обновления. Это и есть причина, по которой копия обязательна.

`SIGTERM` посреди миграции безопасен: миграция идёт в транзакции, прерывание
откатывает её целиком. Опасен `SIGKILL` по истечении срока — поэтому срок с
запасом (решение 5).

### 8а. «Жив» и «готов» — разные вопросы

Сегодняшний `healthcheck` в compose дёргает `/api/health` и отвечает на
вопрос «процесс отвечает». Для установщика и для Docker этого мало: сразу
после старта процесс уже отвечает, а миграции ещё идут, замок ещё не взят и
данные читать рано.

Разводим:

- **жив** — процесс принимает соединения. Это `/api/health`, он остаётся как
  есть и ни от чего не зависит;
- **готов** — замок взят, база открыта, миграции прошли, ключ проверен через
  `vault.check`. Отдельный ответ, и именно его ждёт установщик на шаге 8,
  прежде чем открыть браузер.

**Но `healthcheck` Docker остаётся на «жив», и это осознанно.** Соблазн
повесить его на готовность надо назвать и отвергнуть: состояние «нужна
привязка» после переезда (решение 12) — это законное установившееся
состояние, а не болезнь. Если healthcheck сочтёт его нездоровьем, Docker с
`restart: unless-stopped` начнёт перезапускать Сёму по кругу ровно тогда,
когда человек пытается её настроить. Поэтому: Docker следит за живостью,
готовность показывается человеку и ожидается установщиком.

### 9. Адрес прослушивания и адрес входа

Две разные настройки: `listen_addr` (что слушаем) и `public_origin` (по
какому адресу приходят). Адрес входа выводится из адреса прослушивания
**только если человек его не задавал**; заданный не меняется молча, а
проверяется. Молчаливая правка настройки безопасности — не то, чего ждут от
Сёмы.

Порт занят — **отказ, а не переезд**: порт входит в origin, и самовольный
переезд ломает вход, закладки и адрес в `Sema.app`. Сообщение — диагностика,
а не констатация: занятый адрес, имя настройки, путь к файлу и команда «кто
держит порт» под каждую систему (`lsof -nP -iTCP:8765 -sTCP:LISTEN`,
`ss -ltnp 'sport = :8765'`, `netstat -ano | findstr :8765`). Отдельный
случай — Docker: порт занят пробросом на хозяине, смотреть `docker ps`,
править `ports:` в compose.

**Вход с той же машины не меняется** (`http://127.0.0.1:8765` — защищённый
контекст, RP ID `localhost`). Доступ с телефона требует HTTPS — это условие
мобильного пути, описанное в `web-client`, решения 7 и 8.

### 10. Ключ: одно правило, и `.env` — только способ его подать

**Правило: ключ никогда не хранится рядом с данными в виде, пригодном к
использованию на другой машине.**

На всех целях это переменная окружения, источник — `.env` или
`EnvironmentFile`: **вне тома**, права только владельцу, в `.gitignore`, не
попадает ни в образ, ни в резервную копию. Слабость самой переменной
называем: ключ виден в `docker compose config`, в окружении процесса и в
истории оболочки, если его набирали руками. Это пол, а не хорошее решение,
и он подпирается требованиями к носителю.

**Проверочная запись.** «Проверить фразу, расшифровав существующий секрет»
не работает на пустой Сёме — секретов ещё нет. Поэтому при первой установке
ключа кладётся служебная запись `vault.check`: известная строка,
зашифрованная этим ключом. Ею проверяется и ключ при каждом старте, и фраза
при восстановлении. Не сошлось — Сёма говорит «ключ не тот» сразу, а не при
первой попытке прочитать пароль ящика.

**Фраза восстановления** — единственная резервная копия ключа. Формат:
фиксированная длина, алфавит без похожих знаков, группы по четыре,
контрольная сумма (опечатка отличается от неверной фразы). При вводе
проверяется делом.

**Следствие, которое говорим вслух:** резервная копия — это каталог данных
**плюс** фраза, хранимая отдельно. Копия сама по себе неполна. Интерфейс
обязан это сказать при заведении ключа и при снятии копии.

**Смена ключа существует.** `RotateKey` (`store/secrets.go:179`) уже
перешифровывает секреты и память скриптов; не хватает команды: `sema -rekey`
требует свежей копии, проверяет старый ключ через `vault.check`,
перешифровывает одной транзакцией, обновляет `vault.check`, печатает новую
фразу. Прервалось — прежний ключ остаётся действующим. Старые копии после
смены открываются старой фразой, и об этом сказано.

### 11. Резервная копия с самоосмотром, а не со счётчиками

`sema -backup <файл>`: свести WAL, собрать базу, файлы и опись. Ключ **не
кладётся** — это следует из решения 10. Снимается с работающей Сёмы.

Опись несёт: версию схемы и версию приложения, `sha256` архива и каждого
файла, счётчики предметных записей.

**Счётчиков мало.** «Писем было 12 400, стало 12 400» не доказывает, что
база цела. Поэтому `sema -restore` делает **самоосмотр** и только потом
объявляет результат:

1. сверка `sha256` архива и файлов;
2. `PRAGMA integrity_check`;
3. `PRAGMA foreign_key_check`;
4. проведение миграций схемы до нынешней версии;
5. пробная расшифровка `vault.check` введённой фразой;
6. сверка счётчиков с описью.

Итог — одной строкой: **«проверено»** или **«не сошлось»** с указанием, что
именно. Копия от более новой версии в старую Сёму отклоняется с объяснением,
а не «как-нибудь открывается».

**Файлы и зеркало.** Файлы могут жить не только в томе: при включённом
S3-зеркале часть их снаружи. Опись фиксирует, сколько файлов лежит локально и
сколько только в зеркале; копия без файлов — отдельный режим. Восстановление
на хозяине без доступа к зеркалу проходит, но честно говорит: столько-то
файлов недоступны, вот какие.

### 11а. Ключи пушей переезжают, подписки — нет

Веб-пуши (`web-client`, решение 8) держатся на паре ключей VAPID. Устройство
работы с ними описано там, но у переезда есть своя половина, и она здесь.

Ключи VAPID — обычный секрет в хранилище: шифруются `SEMA_KEY`, попадают в
резервную копию и читаются фразой. Значит **после переезда ключи те же, и
подписки остаются годными** — специально ничего делать не нужно.

Ломается это в двух случаях, и оба надо назвать:

- **сменили ключ шифрования** (`-rekey`) — секреты перешифровались, но сами
  ключи VAPID те же, подписки живы;
- **потеряли или заменили сами ключи VAPID** — все подписки становятся
  негодными разом, потому что браузер привязывает подписку к публичному
  ключу. Тогда Сёма прямо требует переподписать устройства, а не молчит.

Отдельно: подписка привязана к адресу, по которому её заводили. Переехали на
другой адрес — старые подписки перестают быть достижимыми, и это видно по
ответам службы пушей (`404`/`410`), после чего записи удаляются. То есть
**переезд ключи сохраняет, а подписки может обнулить**, и человек об этом
узнаёт из списка устройств, а не из тишины.

### 12. Состояние «нужна привязка» после переезда

Восстановленная Сёма попадает на другую машину: наблюдаемых папок по прежним
путям нет, адреса моделей могут не отвечать. Если просто запуститься, она
начнёт разбирать почту и трогать папки в чужих условиях.

Решение: после восстановления Сёма входит в состояние **«нужна привязка»**, и
в нём **не запускаются наблюдатели папок и приём почты**. Работает интерфейс,
видны данные, доступны настройки. Человек проходит экран привязки: пути
наблюдаемых папок (или выключить), адреса моделей, проверка ключа. После
подтверждения состояние снимается и фоновая работа начинается.

Почему так, а не «запуститься и посмотреть»: приём почты на копии, поднятой
рядом с оригиналом, — это две Сёмы, читающие один ящик и переносящие письма.
Замок от этого не спасает: каталоги-то разные. Состояние «нужна привязка» —
единственное, что стоит между переездом и разбором почты в двух местах.

Отсутствие папки по старому пути **не считается ошибкой данных** и не роняет
задачу.

### 13. Журнал

Формат — строки `время уровень источник сообщение`, читаемые глазами; не
JSON: журнал читает человек, а сборщика логов у нас нет. Уровни `debug`,
`info`, `warn`, `error`, по умолчанию `info`. Объём — 10 МБ на файл, 5
файлов, всё настройки. Маски применяются **до записи**.

**Не попадает никогда:** значение `SEMA_KEY` и любого секрета из хранилища,
пароли ящиков, токены OAuth, заголовки `Authorization` и `Cookie`,
содержимое `.env`, приватные части ключей SSH, сессия Telegram. Правило шире
списка: **значение из хранилища секретов не пишется ни на одном уровне**,
включая `debug` — у `debug` нет права быть опаснее `info`.

### 14. `internal/host` и его границы

Всё, что зависит от системы, — в одном пакете с файлами `_windows.go`,
`_unix.go`, `_darwin.go`; выше по стеку `runtime.GOOS` не спрашивают. Сегодня
таких мест два, и оба показывают, зачем это нужно: `engine/ocr.go:50` и
`google/oauth.go:187` проверяют систему посреди предметного кода, а
`engine/usage.go:179-206` (`Getrusage`, `Statfs`) вообще не собирается под
Windows — и это надо починить даже теперь, когда сборки под Windows нет: тесты
и `go vet` должны проходить.

Наружная поверхность — списком, добавление в неё обсуждается на ревью:

    DataDir() / Lock() / OpenLog() / Stop() / Key()
    Tools() / Doctor() / Backup() / Restore()

Правило: пакет **не знает про почту, модели, модули и память**. Нужен тип из
`engine` или `store` — функция не отсюда.

### 15. Инкременты

**И1. Пути и замок.** Каталог, порядок старта, замок, файловые системы.
**И2. Остановка и WAL.** Сроки, checkpoint, признак чистого закрытия,
инвариант очереди.
**И3. Журнал и `doctor`.** Журнал по решению 13, самопроверка.
**И4. Установщик.** `sema-setup.exe` install/update/remove, таблица бед.
**И5. Переносимость.** `-backup`, `-restore` с самоосмотром, привязка,
`-rekey`.

Порядок обязателен: И2 без И1 бессмысленен, И5 без И2 небезопасен.

**Оценка** (рабочие дни, резерв ~30 %):

| | Дней |
|---|---|
| И1 пути и замок | 5–7 |
| И2 остановка, WAL, инвариант очереди | 6–9 |
| И3 журнал и `doctor` | 4–6 |
| И4 установщик под Windows | 3–5 |
| И5 копия, самоосмотр, привязка, переезд | 8–12 |
| ключ: `vault.check`, фраза, `-rekey` | 4–6 |
| compose, документация, тег, обновление | 2–3 |
| версии и хэши сборок | 2–3 |
| приёмка по целям | 5–7 |
| **Итого** | **39–58** |

После ревью смета не сдвинулась, и это стоит объяснить, а не выдать за
удачу. Прибавили: проба блокировки, разделение «жив/готов», разделение
инварианта очереди на внутренний и внешний, `compose.override.yml`, девять
веток отказа установщика вместо семи, удаление с подтверждением словом.
Убавили: замок стал **проще** (блокировка ОС вместо логики с номерами
процессов и принудительным снятием), Podman ушёл из проверки, мак не трогаем
вовсе — ни миграции каталога, ни XDG. Прибавка и убавка сошлись в пределах
разброса, поэтому 39–58 остаётся.

## Разбор ревью

Девятнадцать замечаний на три изменения. Здесь — те, что про установку;
остальные разобраны в `web-client` и `models-over-network`.

1. **Мак нативно как хозяин противоречит «Docker везде».** Принято. Строка
   убрана из таблицы целей: нативный запуск — режим разработки, не установка;
   Non-Goals приведены в согласие (решение 1).
2. **Каталог данных на маке: XDG против нынешнего `"."`.** Принято, с самым
   тихим решением: **мак не трогаем вовсе**. Он не хозяин, значит и менять
   умолчание незачем — заодно не нужна миграция и нет риска потерять данные.
3. **«Только через `docker exec`» против обслуживаемости.** Принято.
   Решение 1: таблица «задача → команда» (`-backup`, `-doctor`, `-restore`,
   `compose logs`, экспорт) и правило «обслуживание — это команда Сёмы, а не
   поход внутрь контейнера».
4. **«Менять ничего не нужно» про папки на Windows — преждевременно.**
   Принято. Решение 6: это теперь гипотеза с пунктом приёмки и замером, а не
   вывод; не подтвердится — функция объявляется неподдержанной.
5. **PID-замок в Docker не работает.** Принято, и это была настоящая ошибка:
   в контейнере Сёма — процесс 1, «жив ли процесс 1» из соседнего контейнера
   не проверить. Решение 4: блокировка средствами ОС, которую ядро снимает
   само; логика «забрать у мёртвого» и флаг принудительного снятия удалены за
   ненадобностью, номер процесса остался только диагностической записью.
6. **Определение сетевых ФС «на глаз» нереализуемо.** Принято. Решение 4:
   белый список (локальный диск, том Docker) плюс **проба блокировки** при
   старте — проверяем свойство, а не название файловой системы.
7. **Признак чистого закрытия писался после закрытия базы.** Принято, дыра
   была настоящей: писать было уже некуда. Решение 5: пометка «закрываюсь» в
   начале, «закрыт чисто» — последней транзакцией до закрытия, сброс в
   «работаю» при старте.
8. **Checkpoint может не уложиться, а `kill` не даёт срока вовсе.** Принято.
   Решение 5: checkpoint по возможности со своим сроком; опора — поведение при
   следующем старте (проверка целостности и запись в журнал), а не надежда на
   аккуратный выход.
9. **Инвариант очереди слишком общий.** Принято, замечание точное. Решение 5:
   работы разделены на внутренние (транзакция, «ровно один раз») и внешние
   (ключ, отметка «сделано снаружи» до фиксации, проверка перед повтором;
   честное «не более одного раза» для изменяющих).
10. **Установщик описан как последовательность успеха.** Принято. Решение 7:
    таблица из девяти отказов с двумя колонками — что делает установщик и что
    видит человек; добавлен случай «Docker требует перезагрузки».
11. **Автозапуск Docker Desktop не равен службе.** Принято. Решение 3: прямо
    перечислено, когда Сёма **не работает** (до входа в систему, после выхода,
    при выключенном автозапуске, после обновления Windows до входа).
12. **Podman как «запасной, но не поддерживаемый» — ложный путь.** Принято,
    и выбрана вторая ветка: **из документа убран**. Поддержан один Docker
    Desktop; случай «лицензия не подходит» назван нерешённым, а не прикрыт
    непроверенным обходом.
13. **«Одинаков на маке и Windows» — преувеличение.** Принято. Решение 2:
    названы три различия, которые нас касаются (файлы, владелец, сеть).
14. **Версионирование образа и обновление compose.** Принято. Решение 8:
    неизменяемый тег плюс отпечаток; «предыдущая версия» — сохранённые
    `sema.prev` тег и отпечаток; `compose.yml` принадлежит установщику и
    перезаписывается, правки человека живут в `compose.override.yml`.
15. **`healthcheck` не различает «жив» и «готов».** Принято частично.
    Решение 8а: готовность заведена и её ждёт установщик, **но `healthcheck`
    Docker остаётся на живости** — иначе состояние «нужна привязка» будет
    считаться болезнью, и `restart: unless-stopped` начнёт перезапускать Сёму
    ровно тогда, когда её настраивают.
16. **Удаление без политики данных опасно.** Принято. Решение 7: «убрать
    Сёму» и «убрать данные» разведены; второе требует ввести слово, показывает,
    что исчезнет, и предлагает снять копию.
18. **Жизненный цикл ключей пушей не сведён.** Принято. Решение 11а: механика
    осталась в `web-client`, а переезд, копия и смена ключа — здесь;
    разграничено явно.

## Матрица приёмки

Проходится **на каждой цели**: Windows, mac, VPS, Pi.

| Проверка | Ожидание |
|---|---|
| Чистая установка | от нуля до интерфейса в браузере |
| Windows: одна кнопка | `sema-setup.exe` доводит до открытого браузера |
| Windows: нет winget / нет прав / выключена виртуализация | названо словами, повторный запуск продолжает |
| Перезапуск машины | Сёма поднялась сама, замок взят |
| Второй экземпляр на том же томе | не начал работу, сказано почему |
| Два контейнера на одном томе | работает один |
| Грязная остановка (`kill -9`, снятие питания) | поднялась, работы не потеряны, сказано про нештатное закрытие |
| `docker compose up -d` поверх работающей | штатная остановка, WAL сведён |
| Обновление на данных прошлой версии | миграции прошли |
| Откат | восстановление копии в прежнюю версию |
| Копия и восстановление на другом хозяине | итог «проверено» |
| Восстановление с неверной фразой | ничего не перезаписано |
| После переезда | состояние «нужна привязка», почта и папки не запущены |
| Порт занят | диагностика с командой «кто держит» |
| Порт и origin разошлись | предупреждение при старте |
| Ротация журнала | место не кончается, секретов нет |
| Наблюдаемая папка на Windows | файлы принимаются, удаление после приёма выключено |
| Сеть отключена | работа откладывается (см. `models-over-network`) |

## Risks / Trade-offs

- **Docker на Windows — тяжёлое условие.** WSL2, гигабайты, лицензия, BIOS.
  Часть людей отвалится на установке. → Установщик берёт на себя всё, что
  можно, и называет словами всё, что не может. Случай «лицензия не
  подходит» остаётся нерешённым и назван таковым.

- **Переписывание старта ломает работающее.** Замок, остановка и журнал
  трогают `main.go` и `engine` разом. → Делается первым, отдельно, и
  проверяется на нынешней установке в контейнере до всего остального.

- **Замок ошибётся и не пустит Сёму.** Мёртвый файл после `docker kill` —
  хуже задвоения. → Номер процесса, авто-захват, флаг принудительного снятия.

- **Копия без фразы бесполезна, и человек узнает об этом в худший день.** →
  Сказано при заведении ключа и при каждой копии; `-restore` проверяет фразу
  делом.

- **Наблюдаемые папки на Windows медленны и ограничены.** → Только чтение,
  только из профиля, удаление после приёма выключено; опрос вместо событий
  уже работает.
