## Ежедневный осмотр Linux-сервера

Ты смотришь серверы владельца по SSH под пользователем `sema`. Права
**только на чтение**: `sudo` у этих серверов выключен насовсем — команда с
`sudo`, `doas` или `su` не выполнится даже с кнопкой человека. Значит
осмотр строится из того, что видно без root, а нужное право называется
словами в отчёте (см. скилл «Права root на сервере»).

Правила:
- Никогда не выдумывай вывод. Нет прав (`Permission denied`, `Operation not
  permitted`) — так и скажи и назови, какое право нужно (группа `adm` или
  `systemd-journal` для журналов, `sudo wg show` без пароля).
- Одна команда — одна строка, без `sh -c`, без записи в файлы.
  Несколько частей через `|` допустимы, если каждая читающая.
- Ключи не читай: содержимое `authorized_keys`, `.env`, `id_*` тебе не
  нужно. Считай строки, смотри время правки и подписи (третье поле) —
  этого хватает, чтобы заметить чужой ключ.
- На сервере с RouterOS (MikroTik) эти команды не работают — там свой
  скилл.

### Разрешённое: как писать команду, чтобы она выполнилась сама

Команда выполняется без человека, только если ей подходит правило
«Разрешить» этого сервера и разбор Сёмы понял её целиком. Нет подходящего
правила — команда запрещена (человеку приходит карточка «нет правила»).
Проверено на живом разборе — вот на чём команды спотыкались:

- **`2>/dev/null` можно не везде.** У команд со строгой проверкой
  аргументов (`crontab`, `dmesg`, `ip`, `hostnamectl`, `timedatectl`,
  `date`, `mount`) перенаправление считается лишним аргументом, и команда
  перестаёт быть разрешённой. Пиши `crontab -l`, `dmesg -T | tail -20` —
  без хвоста. У `grep`, `cat`, `ls`, `find`, `stat`, `journalctl`, `ss`,
  `apt` — можно.
- **`awk` только в виде `{print $1}`** (можно `-F:` и несколько полей:
  `awk -F: '{print $1, $3}'`). Условия и регулярки внутри awk
  (`awk -F: '$3>=1000 && $7!~/nologin/'`) делают команду неразрешённой —
  отбирай `grep`-ом, а полями режь через `cut` или простой `awk`.
- **`sed` только `sed -n '5p'`.**
- **Скобки, `$(…)`, обратные кавычки, `if`, `for`, `\`** — никогда не
  разрешаются. Вместо `wg show || (systemctl is-active wg-quick@wg0)`
  пиши две отдельные команды.
- **`find … -executable` читается как `-exec`** и не разрешается. Пиши `-perm -u+x`.
- **`reboot` в имени файла — уже не беда**: `ls /var/run/reboot-required`
  и `cat /var/run/reboot-required.pkgs` проходят как чтение.
- Регулярку в кавычках делить на части не будут: `grep -E 'a|b'` цело.

Сомневаешься — разбей команду на две простые. Команда, не попавшая в
разрешённые (она ждёт человека или запрещена), в ежедневном осмотре бесполезна: она никогда не выполнится
сама, а человек утром кнопок не жмёт.

### Блок осмотра: что Сёма выполняет сам

Этот список Сёма читает прямо отсюда и выполняет без вопросов — каждая
строка проверена правилами «Разрешить». Порядок важен: берётся столько строк
сверху, сколько разрешает настройка (`night.look_max`, по умолчанию 12),
поэтому впереди стоит то, без чего осмотр бессмыслен. Правишь список —
проверь новую строку на «Серверы → Правила» («Проверить команду»), иначе
она молча выпадет. Ограждение у блока
особое (`sema-осмотр`): по нему Сёма и находит команды осмотра, а всё
остальное, что скилл показывает кодом, в осмотр не попадает.

```sema-осмотр
apt-get -s dist-upgrade 2>/dev/null | grep -c ^Inst
apt list --upgradable 2>/dev/null | grep -c security
ls /var/run/reboot-required
journalctl -u ssh --since yesterday --no-pager 2>/dev/null | grep 'Failed password' | grep -oE 'from [0-9.]+' | sort | uniq -c | sort -rn | head -5
journalctl -u ssh --since yesterday --no-pager 2>/dev/null | grep Accepted | grep -oE 'from [0-9.]+' | sort | uniq -c | sort -rn
getent passwd | grep -vE 'nologin|false' | cut -d: -f1,3,6,7
getent group sudo adm docker
grep -c '' /home/sema/.ssh/authorized_keys 2>/dev/null
ss -tulpn 2>/dev/null | sort
crontab -l
find /tmp /var/tmp /dev/shm -xdev -type f -perm -u+x 2>/dev/null | head -20
systemctl list-units --state=failed --no-pager | head -10
systemctl list-timers --all --no-pager
find /etc -xdev -type f -mtime -1 2>/dev/null | head -30
ps -eo user,cmd --no-headers | grep -E '/tmp/|/dev/shm/|/var/tmp/' | head -10
ps -eo pid,user,etimes,pcpu,pmem,cmd --sort=-pcpu | head -15
uptime
df -h
free -m
journalctl -p err --since yesterday --no-pager 2>/dev/null | tail -20
```

Ниже — то же самое словами: зачем каждая команда и что считать бедой.

### Что проверять

**1. Обновления и уязвимости.**
`apt-get -s dist-upgrade 2>/dev/null | grep -c ^Inst` — сколько всего.
`apt list --upgradable 2>/dev/null | grep -c security` — сколько закрывают
уязвимости.
`apt list --upgradable 2>/dev/null | grep -E 'linux-image|openssl|openssh|libc6|sudo|wireguard' | head -10`
— важные пакеты поимённо.
`ls /var/run/reboot-required` и `cat /var/run/reboot-required.pkgs 2>/dev/null`
— нужен ли перезапуск и из-за чего; `needrestart -b` — если стоит.

**2. Входы: неудачные и удачные.** Считать мало — важно, откуда.
`journalctl -u ssh --since yesterday --no-pager 2>/dev/null | grep -c 'Failed password'`
— сколько подобрать не смогли.
`journalctl -u ssh --since yesterday --no-pager 2>/dev/null | grep 'Failed password' | grep -oE 'from [0-9.]+' | sort | uniq -c | sort -rn | head -5`
— **с каких адресов**: пять попыток с пяти адресов и пять сотен с одного
это разные новости.
`journalctl -u ssh --since yesterday --no-pager 2>/dev/null | grep 'Invalid user' | grep -oE 'from [0-9.]+' | sort | uniq -c | sort -rn | head -5`
— перебор имён пользователей.
`journalctl -u ssh --since yesterday --no-pager 2>/dev/null | grep Accepted | grep -oE 'from [0-9.]+' | sort | uniq -c | sort -rn`
— **кто вошёл и откуда**; сверяй со вчерашним списком, новый адрес — главная
примета.
`journalctl -u ssh --since yesterday --no-pager 2>/dev/null | grep -c 'Accepted password'`
— вход по паролю там, где ждём только ключи, это уже происшествие.
`last -n 40 -w 2>/dev/null` и `who` — кто входил и кто сидит сейчас.
Журнал закрыт (`No journal files were opened`) — скажи, что нужна группа
`adm` или `systemd-journal`, и не выдумывай нули.

**3. Пользователи, права и ключи.**
`getent passwd | grep -vE 'nologin|false' | cut -d: -f1,3,6,7` — кто может
войти. Новая строка по сравнению со вчера — тревога.
`getent group sudo adm docker wheel root` — кому дана власть. Группа
`docker` это тот же root, только окольным путём.
`ls -la /etc/sudoers.d` и `stat -c '%y %s %n' /etc/passwd /etc/group /etc/sudoers /etc/ssh/sshd_config 2>/dev/null`
— время правки главных файлов: изменились сегодня, а никто не признаётся —
тревога.
`grep -c '' /home/sema/.ssh/authorized_keys 2>/dev/null` — сколько ключей
пускают, `cut -d' ' -f3 /home/sema/.ssh/authorized_keys 2>/dev/null` —
их подписи, `stat -c '%y %n' /home/sema/.ssh/authorized_keys 2>/dev/null` —
когда правили. Ключей стало больше — тревога, даже если подпись знакомая.

**4. Постоянство: чем чужой закрепляется.**
`crontab -l` (без `2>/dev/null`) и `ls -la /etc/cron.d /etc/cron.daily /etc/cron.hourly`
и `cat /etc/crontab` — задания. Строка с `curl`, `wget`, `base64` или
адресом в сети — тревога, даже если файл лежит давно.
`systemctl list-timers --all --no-pager` — таймеры systemd.
`find /etc/systemd /lib/systemd/system /usr/lib/systemd/system -xdev -name '*.service' -mtime -7 2>/dev/null | head -20`
— описания служб, изменённые за неделю.
`systemctl list-unit-files --state=enabled --no-pager` — что включено;
сравнивай со вчерашним списком, новая включённая служба без обновления —
вопрос.

**5. Сеть: кто слушает и куда ходит.**
`ss -tulpn 2>/dev/null | sort` — слушающие порты вместе с процессом.
Сравнивай со вчерашним построчно: **новый порт или новое имя процесса на
старом порту — главная примета**.
`ss -tn state established 2>/dev/null | head -30` — установленные
соединения; связь с незнакомым адресом на 3333, 4444, 5555, 14444 или на
неизвестном порту у процесса, которому в сеть не надо, — примета майнера
или маяка.
`nft list ruleset 2>/dev/null | head -60` или `iptables -S 2>/dev/null | head -40`
или `ufw status verbose` — правила фильтра; исчезнувший `drop` заметнее
нового `accept`.

**6. Файлы, изменённые недавно.**
`find /etc -xdev -type f -mtime -1 2>/dev/null | head -30` — что поправили
в настройках за сутки.
`find /usr/bin /usr/sbin /bin /sbin -xdev -type f -mtime -7 2>/dev/null | head -20`
— новые или подменённые программы: без обновления пакетов там меняться
нечему.
`find /tmp /var/tmp /dev/shm -xdev -type f -perm -u+x 2>/dev/null | head -20`
— исполняемое во временных каталогах. Это почти всегда плохо.

**7. Процессы.**
`ps -eo pid,user,etimes,pcpu,pmem,cmd --sort=-pcpu | head -15` — кто ест
процессор.
`ps -eo user,cmd --no-headers | grep -E '/tmp/|/dev/shm/|/var/tmp/' | head -10`
— процессы, запущенные из временных каталогов.
Имена из случайных букв, `xmrig`, `kdevtmpfsi`, `kinsing`, процесс на
100 % CPU от чужого пользователя — тревога с цитатой строки.
`fail2ban-client status sshd 2>/dev/null` — если стоит.

**8. Службы, ресурсы, журналы.**
`systemctl list-units --state=failed --no-pager | head -10` — упавшие.
`uptime`, `df -h`, `df -i`, `free -m` — диск больше 85 % (или инод больше
85 %) и память меньше 10 % свободной — предупреждение.
`du -sh /var/log 2>/dev/null` и `journalctl --disk-usage` — рост журналов:
внезапно распухший журнал это чаще всего чей-то перебор в него же.
`journalctl -p err --since yesterday --no-pager 2>/dev/null | tail -20` —
ошибки суток.
WireGuard: `wg show 2>/dev/null`; закрыто — `systemctl is-active wg-quick@wg0`
и `ip -br link show` **отдельными командами**, не через `||`. Пир с
`latest handshake` старше двух часов отвалился.
srv-vpn: `systemctl is-active accel-ppp softetherd 2>/dev/null`, затем
`ss -tlnp | grep -E ':443|:1701'`.

### Что считать чем

**Тревога (`alert`) — следы вторжения.** Исполняемое в `/tmp`, `/var/tmp`
или `/dev/shm`; процесс оттуда же; известный майнер по имени; новый
пользователь с оболочкой; новая строка в `authorized_keys`; вход по
паролю там, где ждали ключи; успешный вход с адреса, которого вчера не
было; изменившиеся `sudoers` или `sshd_config`, о которых никто не
предупреждал; новое задание cron с загрузкой из сети; подменённый
файл в `/usr/bin`. Обязательно цитируй строку вывода — без цитаты это
догадка, а не примета.

**Стоит посмотреть (`warn`) — небрежность.** Ждут обновления, особенно
`-security` и ядро; нужен перезапуск; упавшая служба; диск за 85 %; сотни
неудачных входов с одного адреса при неработающем fail2ban; новый
слушающий порт со знакомым процессом; VPN лёг.

**К сведению (`info`).** Обновления есть, но не про безопасность; журнал
закрыт правами; разовые неудачные входы (интернет ими шумит постоянно).

**Спокойно (`ok`).** Ничего из перечисленного.

Не выдавай за примету то, на что не ответишь действием. «Загрузка 0.7» и
«uptime 40 дней» — не новости.

### Ночная смена: разбор, замена, проба

Это про сервер, отданный Сёме целиком (уровень «полная»). В своё окно
Сёма делает всё сам: осмотр → наряд работ → каждый шаг через суд двух
моделей → проба после шага. Шаг — это «что, зачем, одна команда, проба,
возврат»; шага без пробы или без возврата не бывает: такой уходит человеку
карточкой, и это правильный исход, а не неудача. Сервера без sudo смена не
касается вовсе — полной самостоятельности ему не дают.

Три рамки, в которые обязан попасть шаг:

- **Одна команда, одна строка.** `sh -c`, `$(…)`, обратные кавычки, `&&`,
  запись в файл — непонятный синтаксис ночью не выполняется ни при каком
  доверии.
- **Минута.** У ночного шага обычный предел чтения (`ssh.timeout_s`, 60 с);
  десять минут бывает только у команды, которую подтвердил человек.
  `apt-get dist-upgrade` не уложится, оборвётся на середине и остановит
  сервер. Долгое — человеку днём.
- **Возврат — такая же простая команда** на этом же сервере. У команды из
  правила «Спросить» (ключи, пользователи, файрвол, сеть) он заводится
  сторожем **до** изменения и сам вернёт сервер через пять минут, если Сёма
  не подтвердит связь. У обычного шага возврат автоматически никто не
  выполняет: он нужен, чтобы было чем чинить, и чтобы суд видел, что дело
  обратимо. Возврат с подстановками страховкой не заводится — такого шага
  не будет.

**Что смотреть при разборе команды**

1. **Что она трогает** — пакеты, место, службу, сеть, доступ. Всё про
   доступ (`sshd_config`, `authorized_keys`, `ufw`, `iptables`, `nft`,
   `ip route`, пользователи) — правило «Спросить»: ночью только со
   страховкой, и проба обязана проверять сам доступ, а не то, что команда
   вернула ноль.
2. **Обратима ли она этой же ночью.** `rm`, `truncate`, `apt purge`,
   `mkfs`, чистка журналов — вернуть нечем: такому шагу в наряде не место,
   как бы ни хотелось освободить место на диске.
3. **Есть ли копия, на которую обопрётся возврат.** Правишь файл — сначала
   `cp -a /etc/…/файл /etc/…/файл.sema-bak`, и возврат становится честным:
   `cp -a /etc/…/файл.sema-bak /etc/…/файл`.
4. **Точна ли цель.** Маска `*`, `-r`, `--all`, «все старые» — ночью только
   поимённо: один пакет, одна служба, одно правило.
5. **Кого заденет.** Перезапуск рвёт чужие соединения, чистка `/tmp` уносит
   чужие файлы, `reload` мягче `restart` и почти всегда достаточен.
6. **Что будет, если оборвётся посередине.** Полдела хуже, чем ничего.

**Чем заменять опасное**

- `apt-get dist-upgrade` целиком → один пакет:
  `apt-get -y --only-upgrade install openssl`. Ядро, `libc6`, `systemd` и
  всё, после чего нужен перезапуск, — человеку: ночную перезагрузку никто
  не увидит, а возврата у неё нет. Прежнюю версию для возврата узнавай
  **до** обновления (`dpkg -l openssl`): сама установка прежней версии
  (`apt-get -y --allow-downgrades install openssl=<версия>`) — правило
  «Спросить».
- `rm -rf /var/log/*`, `truncate`, `journalctl --vacuum-…` → ничего из
  этого. Удаление необратимо, и возврат к нему не придумывается. Кэш
  пакетов чистится безобидно (`apt-get clean`, скачается заново), а про
  распухший файл честнее доложить: `du -sh /var/log`,
  `find /var/log -type f -size +100M 2>/dev/null | head -10`.
- `systemctl restart` → `systemctl reload`, если служба умеет (nginx, ssh,
  cron): настройки перечитываются, соединения живут. Упавшую службу
  поднимают `systemctl start <служба>`, и возврат у этого честный —
  `systemctl stop <служба>`.
- `kill -9` → `systemctl restart <служба>`: службу вернёт система. Чужой
  процесс ночью не твоё дело, про него пишут человеку.
- `ufw`/`nft flush`/`iptables -F` → точечное правило со страховкой, и
  возврат снимает ровно его: `ufw allow 8443/tcp` ↔
  `ufw delete allow 8443/tcp`. Массовая чистка правил — человеку всегда.
- Правка `sshd_config` → копия рядом, правка, проверка отдельным шагом
  (`sudo sshd -t`) и `systemctl reload ssh`, а не `restart`: reload не рвёт
  живые сессии, и дверь остаётся открытой.
- `chmod -R`, `chown -R`, `dd`, `mkfs`, `fdisk`, `userdel`, `passwd` —
  ночью не бывает никогда.

**Какой пробой проверять**

Проба — читающая команда: Сёма выполняет её сам, и если она не разрешена
правилами сервера (см. раздел выше), шаг считается непроверенным, а сервер
останавливается. `nginx -t` пробой быть не может — это не чтение;
`systemctl is-active nginx` может. Проба должна **опровергать беду**, а не
подтверждать, что команда вернула ноль:

- обновили пакет → `dpkg -l openssl | grep ^ii` и
  `apt-get -s dist-upgrade 2>/dev/null | grep -c ^Inst` (ждущих стало меньше);
- тронули службу → `systemctl is-active <служба>`, следом
  `systemctl list-units --state=failed --no-pager | head -10`;
- освободили место → `df -h /` и `df -i /`;
- тронули сеть, порт или ssh → `ss -tulpn 2>/dev/null | grep -c :22` и
  `ip -br addr`; связь Сёма проверяет и сам, отдельным новым соединением,
  но проба обязана назвать именно тот порт или правило, которого коснулись;
- тронули расписания → `crontab -l`,
  `systemctl list-timers --all --no-pager`;
- тронули журналы → `journalctl --disk-usage`, `du -sh /var/log`.

`uptime`, `echo ok` и «команда прошла» — не пробы: они сойдутся всегда.
Нечем проверить шаг — значит шага не будет.

### Отчёт: одна запись на все серверы

Человек просил краткий отчёт, и это значит **одну запись в «Уведомлениях»
про все серверы сразу**, а не простыню в чате и не по записи на сервер.

Норма — одна строка и всё:
`Пять серверов, всё спокойно`.

Есть что сказать — в заголовке только то, что не спокойно:
`srv-bots: 47 неудачных входов с одного адреса, 12 пакетов ждут · остальные спокойно`.

Подробности — полями, по строке на сервер: подпись — имя сервера,
значение — его короткий итог, уровень — его уровень. Спокойный сервер
тоже строкой, но с уровнем `ok`.

Уровень всей записи — худший из серверов: следы вторжения — `alert`,
обновления и упавшие службы — `warn`, спокойно — `ok`.

Изменение (обновить пакеты, перезапустить службу) предлагается **действием
записи**, а не выполняется: у этих серверов sudo выключен, так что честно
скажи, что команду выполнит человек на самом сервере, и назови её.
В чат не пиши ничего: запись в «Уведомлениях» и есть отчёт.

### Ответ модели в модуле — JSON, не текст

Когда тебя зовёт модуль (`sema.llm` с этим скиллом и выжимкой по всем
серверам), отвечай ТОЛЬКО JSON без пояснений:

```json
{"level": "warn",
 "summary": "srv-bots: 47 неудачных входов с 203.0.113.10, 12 пакетов ждут · остальные спокойно",
 "fields": [{"label": "srv-bots", "value": "47 неудачных входов с 203.0.113.10 · 12 обновлений, security 3 · порты без изменений", "level": "warn"},
            {"label": "WireGuard", "value": "спокойно · пиров 3, все на связи", "level": "ok"},
            {"label": "srv-vpn", "value": "спокойно · нужен перезапуск после ядра", "level": "info"},
            {"label": "Microtik", "value": "спокойно · RouterOS 7.16.2", "level": "ok"},
            {"label": "Что смотрели", "value": "входы, ключи, порты, cron и таймеры, файлы в /etc и /tmp, процессы, обновления"}],
 "actions": [{"label": "Обновить пакеты на srv-bots", "ssh": "srv-bots", "cmd": "apt-get -s dist-upgrade"}]}
```

`level`: `ok` — всё спокойно; `info` — есть что знать, делать нечего;
`warn` — обновления, упавшая служба, полный диск; `alert` — приметы
вторжения. `actions` — пустой список, если делать нечего. Нет прав на
команду — поле с `level: "info"` и текстом «нет прав: нужна группа adm»,
не выдумывай значение.

### Как оформить регулярный осмотр

Осмотр делает модуль, а не серия скриптов: манифест с
`needs: ["ssh", "llm", "schedule", "store"]`, `ssh` — список серверов,
`skills: ["linux-admin", "mikrotik"]`, задача `check` с расписанием `8:00`.

В коде: по каждому серверу выполняй команды из раздела «Что проверять»
через `sema.ssh.run(host, cmd)`, собирай **короткие** выдержки — счётчики,
первые 15 строк, журналы уже отобранными `grep`-ом. Складывай выжимку в
`sema.store.set` или `sema.data.put('daily', host + ':' + date, …)`, чтобы
сравнить с вчерашней: новые пользователи, новые порты, новые ключи, новые
адреса входов видны только сравнением.

Модели отдавай **одним запросом выжимку по всем серверам сразу** вместе с
этим скиллом — иначе она не сможет сказать «остальные спокойно» и напишет
по записи на сервер. Разбери JSON из ответа
(`s.slice(s.indexOf('{'), s.lastIndexOf('}') + 1)`) и положи **одну**
запись:

```js
sema.notify({key: 'servers:daily', title: r.summary, level: r.level,
             summary: r.summary, fields: r.fields, actions: r.actions});
```

Ключ один и тот же каждый день — новая запись заменяет вчерашнюю, и в
«Уведомлениях» не копится по четыре строки за утро. JSON не разобрался —
`sema.notify({key: 'servers:daily', title: 'Осмотр серверов · отчёт не
разобран', level: 'warn', fields: [{label: 'Ответ модели', value: raw}]})`:
молчать нельзя, молчание неотличимо от «всё хорошо».

Ответы инструментов: `sema.ssh.run` возвращает `{output, code}` для
выполненной команды и `{pending, why}` для той, что ждёт подтверждения
(не ошибка) — бери `r.output`, не `String(r)`. Команда, вернувшая
`{pending}`, в осмотре бесполезна: перепиши её по разделу «Разрешённое».
`sema.store.get/set` хранят строки — объекты через `JSON.stringify` и
`JSON.parse`; `sema.data.put/get` хранят JSON как есть.
